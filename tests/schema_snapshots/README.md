# Schema snapshots

Frozen DDL of the database at past schema versions. `tests/test_schema_upgrade_path.py`
loads each one into an empty file, stamps `schema_version`, runs `Database.bootstrap()`
and asserts the upgraded database is indistinguishable from a freshly bootstrapped one.

Without these, nothing in CI exercises the path every production deploy takes — an
*existing* database meeting new code. That gap is how a baseline `CREATE INDEX` on
`key_bundles.display_no` (a column `_migrate_v33` adds) passed CI twice and then
crash-looped the bot on a live v32 database.

| File | What it is |
| --- | --- |
| `vNN.sql` | Generated by `scripts/dump_schema_snapshot.py` — do not hand-edit. |
| `vNN.seed.sql` | Optional, hand-written. Rows loaded right after `vNN.sql`, so migrations run against a populated database and backfills are actually exercised. |

`v29`–`v32` were dumped from the tree at each version's last commit, so they are the
real schemas, not reconstructions. Versions older than 29 predate this repository's
history and cannot be captured authentically.

## Adding one

Before bumping `CURRENT_SCHEMA_VERSION`, on the tree that still has the old value:

```bash
python scripts/dump_schema_snapshot.py     # writes tests/schema_snapshots/v<OLD>.sql
```

Then commit it with the migration. `test_previous_version_snapshot_exists` fails the
build if this step is skipped, so the ladder cannot silently develop a hole.
