# Синхронизация бэкенд-конфигов — два файла с совладением

У Hysteria2 есть трекнутый устанавливаемый конфиг (`deploy/hysteria/config.yaml` +
`deploy/hysteria/install-config.sh`). У Xray и AmneziaWG — нет, и долгое время это
выглядело как недоделка. Это не она: асимметрия вытекает напрямую из того, **кто пишет
файл в рантайме**.

Эта страница — про получившийся механизм: что трекается для этих двух бэкендов, как хост
сверяется с репозиторием и в каком единственном случае репозиторий можно накатить на хост.

## Почему три бэкенда обслуживаются по-разному

| Живой файл | Кто пишет в рантайме | Можно ли скопировать из репо? |
|---|---|---|
| `/etc/hysteria/config.yaml` | **Только оператор.** Бот пишет строки в БД, а `hy2_auth` аутентифицирует handshake по живой БД. Сам файл не перезаписывает никто. | **Да** — `deploy/hysteria/install-config.sh`, который подставляет stats-секрет, чтобы плейсхолдер не попал на диск. |
| `/usr/local/etc/xray/config.json` | **Совладение.** Бот перезаписывает файл целиком на каждой выдаче/отзыве ключа (`adapters/xray_config.py`, `os.replace` в конце apply-пути). | **Нет.** `cp` удалил бы все выданные клиенты и short ID. |
| `/etc/amnezia/amneziawg/awg0.conf` | **Совладение.** Бот перезаписывает файл целиком на каждой вставке/удалении пира (`adapters/awg_config.py`, через `backup.atomic_write_text`). | **Нет.** `cp` удалил бы все выданные пиры. |

То есть для двух файлов с совладением репозиторий не может трекать *конфиг*. Но он может
трекать — и теперь трекает — **их структуру**, оставив пустыми все области, которыми
владеет бот:

- `deploy/xray/config.skeleton.json`
- `deploy/awg/awg0.conf.example`

В обоих вместо значений стоят плейсхолдеры (`<REALITY_PRIVATE_KEY>`,
`<AWG_SERVER_PRIVATE_KEY>`, …) — поэтому их безопасно коммитить и безопасно читать на
общем хосте.

## Границы владения, точно

Это то самое единственное определение, из которого выведено всё остальное. Оно
зафиксировано `tests/test_backend_config_sync.py`: тесты дёргают **настоящих писателей** и
проверяют, что чекер правильно классифицирует то, что те написали. Поэтому писатель,
который перенёс список клиентов или переименовал маркер пира, ломает тесты, а не прод.

**Xray — боту принадлежит:**

| Область | Кто пишет |
|---|---|
| `inbounds[*].settings.clients` | `XrayConfigAdapter._clients()` — по записи на каждый выданный ключ VLESS / VLESS (HTTP) |
| `inbounds[*].streamSettings.realitySettings.shortIds` | `XrayConfigAdapter._reality_settings()` |
| `outbounds[*].sendThrough` **только при `protocol: freedom`** | `apply_warp_send_through()`, переутверждается при *каждой* записи конфига |

Всё остальное в `config.json` — структура оператора: теги и порты inbound'ов, REALITY
`target` и `serverNames`, топология fallback'ов, `routing`, `dns`, `policy`, `api`, `log`.

**AmneziaWG — боту принадлежит:**

| Область | Кто пишет |
|---|---|
| Блоки `[Peer]`, ограниченные `# vpn-bot peer start key_id=<N> owner=<UID>[ label=<L>]` … `# vpn-bot peer end key_id=<N>` | `AwgConfigAdapter._peer_block()` |

`[Interface]` целиком принадлежит оператору. Бот его читает (`read_server_config`) и
переносит дословно при каждой перезаписи.

> ⚠️ Обфускационный отпечаток AmneziaWG — `Jc`/`Jmin`/`Jmax`, `S1`–`S4`, `H1`–`H4`,
> `I1`–`I5` — это часть идентичности деплоя, а не настройка. Бот копирует эти значения из
> `[Interface]` в каждый клиентский конфиг, и handshake не завершается, если сервер и
> клиент не совпадают байт в байт. Поменяв одно из них на сервере, вы молча
> инвалидируете **все уже выданные ключи**.

## Проверка хоста: `check`

Только чтение. Сверяет живые файлы с трекнутыми скелетами, исключив все области бота, —
поэтому рантайм-состояние не может быть показано как расхождение.

```bash
python3 deploy/backend-config-sync.py check
python3 deploy/backend-config-sync.py --selftest      # прогоняет саму логику сравнения
```

Дефолтные пути — те же, что использует deploy.sh; переопределяются через `--repo-root`,
`--xray-config` и `--awg-config`.

Что делает сравнение:

- **Плейсхолдеры — это wildcard.** `<REALITY_PRIVATE_KEY>` совпадает с любым значением,
  поэтому для работы проверки секреты не нужны в репозитории. Для частично-литеральных
  значений вроде `PostUp` текст *вокруг* плейсхолдеров всё равно проверяется — замена
  `MASQUERADE` → `SNAT` ловится, хотя подсеть и интерфейс остаются плейсхолдерами.
- **Inbound'ы сопоставляются по `tag`, а не по позиции.** Xray не важен порядок
  inbound'ов — значит, не важен и чекеру.
- **Сравнение строгое по типу.** JSON `true` и `1` — разные значения; конфиг, съехавший с
  одного на другое, будет показан.
- **Отсутствующий бэкенд — не расхождение.** На хосте только с Hysteria2 нет
  `config.json` — чекер сообщает об этом как INFO и выходит с 0. Та же политика
  `absent-ok`, что у out-of-repo хелперов в deploy.sh.
- **Состояние бота показывается, но не сравнивается.** В выводе есть перепись (клиенты по
  тегам inbound'ов, пиры: всего / под управлением бота / добавленные руками) — оператор
  видит рантайм, но на вердикт это не влияет.
- **Пир, добавленный руками, выводится как INFO.** Это не ошибка конфига, но блок
  `[Peer]` без маркера `vpn-bot` невидим для бота и при этом занимает адрес из
  `AWG_NETWORK` — поэтому молча он не проходит никогда.

Коды выхода — это и есть контракт с deploy.sh:

| Код | Значение |
|---|---|
| `0` | Структурных расхождений нет (или бэкенд здесь не развёрнут). |
| `1` | **Fail-closed:** вердикт недостижим — нечитаемый живой конфиг, отсутствующий скелет. |
| `2` | Ошибка использования. |
| `3` | Найдено структурное расхождение. |

## Гейт в Phase 1

`scripts/deploy.sh` запускает `check` в Phase 1 против worktree `origin/main` (`$WT`), а
не против локального чекаута — так же, как сканируется расхождение по юнитам. Поэтому PR,
который законно меняет форму data plane, ловится **до** перезапуска, а не после.

Расхождение останавливает деплой. Чекер не может знать, какая сторона неправа, поэтому
отчёт печатает оба маршрута:

```bash
# Неправ ХОСТ — репозиторий и есть замысел:
python3 deploy/backend-config-sync.py install-xray --dry-run   # посмотреть слияние
python3 deploy/backend-config-sync.py install-xray             # затем применить
sudo systemctl restart xray                                    # окно выбираете вы
# У AWG установщика нет намеренно — правьте awg0.conf руками (см. ниже)

# Неправ РЕПОЗИТОРИЙ — замысел на хосте:
#   обновите deploy/xray/config.skeleton.json или deploy/awg/awg0.conf.example
```

`ALLOW_BACKEND_CONFIG_DRIFT=1` проходит гейт насквозь. Применять только осознанно:
расхождение уже известно и безопасно, либо вы деплоите ровно тот коммит, который приведёт
скелет в соответствие, и сразу после этого запустите `install-xray`. Это **никогда** не
замена обновлению скелета, когда правильная сторона диффа — хост.

Код выхода `1` намеренно **не** обходится этой ручкой: нечитаемый `config.json` — это не
расхождение, которое можно списать, это сломанный data plane; собственный писатель бота на
нём тоже упадёт.

> Поскольку области бота исключены из сравнения, находка здесь — *всегда* структура
> оператора. Выдача и отзыв ключей не могут покрасить Phase 1 в красный, и именно это не
> даёт ручке превратиться в рефлекс.

## Накатить репозиторий на хост: `install-xray`

Это слияние, а не копирование: структуру даёт скелет, а все области бота и все секреты
оператора — живой файл.

```bash
python3 deploy/backend-config-sync.py install-xray --dry-run    # печатает слитый конфиг
python3 deploy/backend-config-sync.py install-xray
sudo systemctl restart xray
```

Свойства безопасности, в порядке их проверки:

1. **Отказывается работать, если живого конфига нет.** Приватный ключ REALITY существует
   *только* в живом файле, поэтому пути bootstrap здесь нет: слияние с пустотой записало
   бы `<REALITY_PRIVATE_KEY>` в несущий конфиг.
2. **Отказывается, если в живом конфиге нет списка `clients`.** Такой конфиг инструмент не
   понимает, а догадки стоили бы ключей.
3. **Плейсхолдеры разрешаются сначала из `.env`, затем из живого значения по тому же
   пути.** `.env` — это замысел оператора (`XRAY_SNI`, `XRAY_XHTTP_PATH`), живой файл —
   лишь текущее состояние. Плейсхолдер, у которого нет ни одного источника, — это отказ
   fail-closed, а не литерал `<...>` на диске.
4. **Клиенты, short ID и `sendThrough` возвращаются на место по `tag` inbound'а, а не по
   индексу**, и количество клиентов после слияния сверяется с живым. Скелет, назвавший
   inbound, которого на хосте нет, молча потерял бы ключи этого inbound'а — проверка ловит
   это до того, как что-либо записано.
5. **`xray run -test` должен принять слитый конфиг.** Если бинарника нет или он отверг
   результат — не записывается ничего: невалидированный конфиг поверх живого уронит `:443`
   на следующем перезапуске, а собственные записи бота потом упадут на файле, который он не
   может разобрать.
6. **Режим и владелец сохраняются**, предыдущий конфиг остаётся как `config.json.pre-sync`,
   замена атомарная (`os.replace`).
7. **Xray никогда не перезапускается.** Выбор окна — за оператором.

При нулевом расхождении слияние *семантически идентично* живому конфигу — меняется только
форматирование. Именно это свойство и делает установщик безопасным.

> Запускайте с остановленным ботом или в Phase 2 деплоя (deploy.sh останавливает юнит бота
> перед Phase 2), чтобы слияние не гонялось с собственным `ConfigFileLock` бота.

### Почему у AmneziaWG установщика нет

`[Interface]` принадлежит оператору *целиком*, и каждое значение в нём — либо секрет, либо
часть обфускационного отпечатка. Инструменту тут нечего сливать: либо прав хост и обновить
надо пример, либо неправ хост, и тогда починка — ручная правка, чей радиус поражения (все
выданные ключи) оператор должен взвесить лично. `check` расхождение всё равно покажет;
применение намеренно ручное.

## Bootstrap на чистом или переехавшем хосте

Ни один из скелетов не устанавливается деплоем — никогда. Это разовые действия оператора.

**Xray.** Скелет — точка старта для `config.json`, а не drop-in: в нём нет пары ключей
REALITY и ещё нет `.env`.

```bash
umask 077
install -o root -g root -m 0600 deploy/xray/config.skeleton.json \
    /usr/local/etc/xray/config.json
xray x25519                                   # сгенерировать пару ключей REALITY
# заменить все <PLACEHOLDER>, затем:
xray run -test -config /usr/local/etc/xray/config.json
sudo systemctl restart xray
```

Публичная половина идёт в `.env` как `XRAY_REALITY_PUBLIC_KEY`; приватная остаётся в
`config.json` и больше нигде. Остальная разовая настройка Xray — API-inbound, тег, который
ищет бот, и drop-in на одиночный конфиг, которым владеет upstream-установщик, — в
[deployment.ru.md](deployment.ru.md#разовая-подготовка-сервера); топология fallback'ов
XHTTP — в [xray-xhttp-inbound.ru.md](xray-xhttp-inbound.ru.md).

**AmneziaWG.** Никогда — поверх конфига, в котором уже есть пиры.

```bash
umask 077
install -o root -g root -m 0600 deploy/awg/awg0.conf.example \
    /etc/amnezia/amneziawg/awg0.conf
# пара ключей сервера, не оставляя приватную половину на диске в открытом виде:
priv="$(awg genkey)"
printf 'PrivateKey = %s\n' "$priv"                          # -> [Interface].PrivateKey
printf 'AWG_SERVER_PUBLIC_KEY=%s\n' "$(printf %s "$priv" | awg pubkey)"   # -> .env
unset priv
# заменить все <PLACEHOLDER>, затем:
awg-quick strip awg0 >/dev/null && sudo systemctl start awg-quick@awg0
```

Публичная половина идёт в `.env` как `AWG_SERVER_PUBLIC_KEY`. Пример намеренно поставляется
с **нулём** блоков `[Peer]`: пиры — это рантайм-состояние, а написанный здесь руками пир был
бы невидим для бота, но всё равно занимал бы адрес из `AWG_NETWORK`.

## Что уже было закрыто и не является задачей этого механизма

`scripts/deploy.sh` всегда считал sha256 обоих файлов до и после Phase 2, чтобы решить,
нужен ли бэкенду перезапуск, и складывал копию каждого в бэкап деплоя (`stage_path`).
То есть **восстановление** дыркой никогда не было — плохой деплой и раньше можно было
откатить. Не хватало другого: bootstrap, ревью структурных изменений до того, как они
уедут, и вообще любого сигнала, что хост и репозиторий разошлись. Это и добавляет
описанный механизм.
