# HTTP-эндпоинт all-in-one подписки

**Отдельный процесс** (`python -m subscription_server`, юнит
`deploy/vpn-bot-subscription.service`) с единственным маршрутом — `GET /sub/{token}`, — который
отдаёт base64-подписку бандла: все его дочерние ключи в виде обычных клиентских ссылок. По
умолчанию **выключен** (`SUBSCRIPTION_ENABLED=false` — тогда на любой запрос отвечает `404`, а
бот не показывает про бандлы ничего).

Канонические справочники лежат там же, где и для остальных фич:

- **Переменные окружения** → [Конфигурация → All-in-one подписка](configuration.ru.md#all-in-one-подписка).
- **Семантика бандлов** (состав, отзыв, удаление) → тот же раздел.

## Как это работает

1. Клиент запрашивает `https://<host>:<публичный-порт>/sub/<token>`; токен — это секрет бандла
   (`key_bundles.token`, 256 бит, URL-safe) и **единственный** креденшл.
2. Эндпоинт читает `vpn.db` **только на чтение, вживую, через обычные репозитории** — без кэша.
   Поэтому отзыв, ротация токена или удаление действуют уже на следующем запросе, без рестарта,
   и эндпоинт продолжает работать, пока `vpn-bot.service` лежит.
3. Каждый ACTIVE-ребёнок ACTIVE-бандла рендерится **тем же кодом, что и одиночная выдача ссылки**
   (`XrayService._build_vless_link` для VLESS TCP/HTTP, `bot.formatters.format_hysteria2_link`
   для Hysteria2), ссылки склеиваются через `\n` и кодируются в base64. Ничего другого в
   подписку не попадает: AWG и прокси SOCKS5/MTProto исключены из состава бандла, поэтому строка
   любого другого типа роняет рендер целиком, а не молча пропускается.
4. Порядок ссылок и их названия задаются **видом** бандла — см.
   [Два вида all-in-one](#два-вида-all-in-one) ниже. Порядок берётся из
   `services.key_bundles.subscription_sort_key()` (выводится из шва состава, а *не* из `id`
   детей — иначе бандл, созданный до смены порядка, отдавался бы в старом): **сначала все прямые
   дети, потом все relay-дети**, внутри каждой группы — порядок состава. **Расширенный** бандл
   добавляет к названию каждой записи через нижнее подчёркивание кружок предпочтительности:

   | Порядок | Участник | Кружок |
   |---|---|---|
   | 1 | VLESS (TCP) | 🟢 |
   | 2 | Hysteria2 | 🟢 |
   | 3 | VLESS (HTTP) `base` | 🟡 |
   | 4 | VLESS (HTTP) `multi` | 🟠 |
   | 5 | VLESS (HTTP) `antisib` | 🔴 |

   У **базового** бандла кружков нет: его участники называются как одиночные ключи, с флагом
   сервера. Название живёт **только** в `#fragment` ссылки — хранимый `email_label` (email
   клиента Xray, auth-id hy2) не меняется, поэтому reconcile, статистика трафика и детект
   аномалий продолжают матчиться по нему. Бот объясняет цвета на экранах расширенной подписки (и
   только там); в том же порядке выводится и «Состав».
5. **spiderX (`spx`) у VLESS-детей может ротироваться.** При `XRAY_SPIDER_X_ROTATION_HOURS=0`
   (дефолт) каждый ребёнок несёт свой сохранённый `spx`, ровно как его одиночная ссылка. При
   значении `> 0` и непустом `XRAY_SPIDER_X_POOL` `spx` каждого ребёнка проходит по пулу, по
   одной записи за период, переключаясь в свою секунду; рендерер читает часы **один раз на
   ответ**. Ничего не записывается обратно — значение есть чистая функция от UUID ключа, пула,
   периода и времени, поэтому экран «Конфиг» того же ребёнка в боте (доступен из админского
   просмотра ключей пользователя) в ту же секунду показывает то же значение. Ссылки Hysteria2 и
   заголовки ответа не меняются. Алгоритм и правила:
   [Конфигурация → ротация spiderX](configuration.ru.md#xray-vless-reality).

### Два вида all-in-one

Вид выбирается в мастере создания (экран после предупреждения про AmneziaWG, где описаны оба
вида) и хранится в `key_bundles.kind`. Пользователь потом сменить его не может; сменить вид
можно только админским массовым приведением, см.
[Приведение существующих подписок](#приведение-существующих-подписок).

| | базовая (`basic`) | расширенная (`extended`) |
|---|---|---|
| Участники | VLESS (TCP), Hysteria2 | VLESS (TCP), Hysteria2, VLESS (HTTP) `base` / `multi` / `antisib` |
| На каждый relay (включён и «в подписках») | + те же 2 → **4** с одним relay, **6** с двумя | + те же 5 → **10** с одним relay, **15** с двумя |
| Название записи | `<label>[_<метка relay>]_<SERVER_FLAG_EMOJI>` | `<label>[_<метка relay>]_<кружок>` |
| Подсказка про кружки («⚠️ Кружок в конце названия…») | не показывается нигде | на экранах бандла |

- Все бандлы, существовавшие до появления вида (схема v37), — **расширенные** и отдаются ровно
  как раньше: те же участники, те же названия `<label>_<кружок>`, основной хост.
- **Relay-участник** ([docs/relay.ru.md](relay.ru.md)) — тот же участник протокола, что и его
  прямой двойник (тот же путь создания, тот же префикс метки), поэтому в расширенном бандле у
  него **кружок двойника**: `xray_http_multi_ab12c_relay_🟠`.
- Relay-участники создаются для каждого relay, который в админ-панели **включён и «в
  подписках»** на момент создания бандла, группами в порядке `id` relay: все прямые участники,
  затем через relay №1, затем через relay №2, … В бандле, созданном без таких relay, их нет, а
  добавление или включение relay позже существующий бандл само по себе не дополняет — это
  делает админское массовое приведение
  ([Приведение существующих подписок](#приведение-существующих-подписок)).
- Endpoint читает таблицу `relays` на каждый запрос, поэтому host или метка relay, изменённые
  в панели, отдаются со следующего запроса без рестарта.
- Relay-участник, чей relay выключен или удалён, **пропускается** с `WARNING` в логе,
  остальная подписка отдаётся (`200`). Это единственное намеренное исключение из правила
  «ребёнок, который не рендерится, роняет весь ответ»: выключение relay — решение оператора, а
  не битая строка. Бандл, которому нечего отдать, — по-прежнему обычный `404`.

Ссылка одиночного ключа везде, где её показывает бот (экран конфига, QR, мастер создания),
называется `<label>[_<метка relay>]_<SERVER_FLAG_EMOJI>` — `xray_tcp_ab12c_🇫🇮`,
`hy2_x7k2p_relay_🇫🇮` (`relay` — метка relay по умолчанию; у каждого relay она задаётся в
админ-панели).

### Приведение существующих подписок

Бандл сохраняет состав, с которым был создан: включение relay или включение/выключение
протокола существующие бандлы само по себе не меняет. Superadmin приводит их к нужному составу
в админ-панели → **«🔗 All-in-One»** (кнопка есть только при `SUBSCRIPTION_ENABLED=true`):

- **«Перевести все подписки в базовый вид»** — каждая активная подписка получает тот состав,
  который сейчас получила бы **новая базовая**: VLESS (TCP) и Hysteria2, а также их копии через
  каждый relay, включённый и «в подписках» («🛰 Управлять relay»). **Дети VLESS (HTTP) удаляются** (клиент в
  backend, строка в БД, трафик уходит в архив удалённых ключей, аудит — тот же путь, что
  удаление ключа), недостающие участники создаются, вид становится `basic`.
- **«Дополнить все подписки по текущим настройкам»** — то же без смены вида: например,
  добавляет участников через relay после того, как его добавили или включили «в подписки».

Обе операции начинаются с **dry-run** по всем активным подпискам — «подписок N, будет создано
X ключей, удалено Y», плюс какие подписки будут пропущены и почему — и ничего не меняют до
подтверждения. Затем прогон идёт по подпискам последовательно в фоне, сообщение о прогрессе
обновляется не чаще раза в 3 с; ошибка одной подписки не останавливает остальные, итоговое
сообщение перечисляет изменённые, пропущенные (с причиной) и ошибки.

Правила для каждой подписки:

- **Токен подписки не меняется** — у пользователей остаётся та же ссылка; клиент получит новый
  состав при следующем обновлении.
- Цель — ровно то, что сейчас создало бы создание бандла (тот же seam состава и тот же фильтр
  «backend выключен → участник не входит»). Недостающие участники создаются для владельца
  бандла с его заметкой, общим `expires_at` детей и fingerprint существующего VLESS-ребёнка;
  дети вне цели удаляются. Это касается и участников relay, который на момент прогона
  **выключен или не «в подписках»**, — если relay выключен лишь временно, проверьте план перед
  подтверждением.
- Сначала все создания; если одно упало — созданное в этом прогоне откатывается, подписка
  остаётся как была. Затем удаления; если одно упало — подписка остаётся приведённой частично, и
  **повторный запуск доделывает** — в том числе ребёнка, которого упавший откат оставил в
  `delete_failed`. Вид меняется последним. Уже приведённую подписку прогон не
  трогает, так что повторный запуск — no-op.
- Подписка **пропускается без изменений**, если в ней что-то необычное: два активных ребёнка на
  одном месте состава, разные сроки действия у детей, неактивный ребёнок-участник (например,
  отозванный отдельно), ни одного активного ребёнка (срок истёк) или degraded backend, который
  затронет изменение. Обрабатываются только `active`-подписки.
- Каждое создание и удаление VLESS-ключа — одно применение конфига Xray (при
  `XRAY_APPLY_MODE=restart` — один рестарт Xray), ровно как создание или удаление одиночного
  ключа.
- **Остановка бота посреди прогона** (рестарт, деплой): прогон доделывает текущую подписку и
  останавливается до закрытия БД (ждём до 60 с); в отчёте посчитаны необработанные подписки —
  для них запустите операцию снова.

### Fail-closed

Любой отказ — это **один и тот же пустой `404`**: неизвестный токен, отозванный бандл, удалённый
бандл, бандл без активных детей, битая строка ребёнка, нечитаемая БД и выключенный флаг. Отличить
никогда не существовавший токен от отозванного нельзя, частичный конфиг не отдаётся никогда.
`5xx` эндпоинт не отдаёт вообще: неожиданная ошибка перехватывается и превращается в тот же
`404`, так что трейс наружу не уходит. Единственный другой статус — `429` (с `Retry-After`, в нём
остаток текущего окна) от рейт-лимита, который срабатывает **до того, как токен вообще смотрят**,
— поэтому отказ не выдаёт и факт существования токена. Лимит — фиксированное окно:
`SUBSCRIPTION_RATE_LIMIT_BURST` запросов на `SUBSCRIPTION_RATE_LIMIT_SECONDS` на клиента, где
клиент — адрес пира (весь NAT делит один бакет, из-за чего burst и не равен 1). Отказ окно не
продлевает и пишется в лог на уровне `WARNING` — только бакет, без токена.

### Заголовки ответа

| Заголовок | Значение |
|---|---|
| `Profile-Title` | Метка бандла (`bundle_XXXXX`); в `base64:` заворачивается только не-ASCII метка, отредактированная руками. |
| `Profile-Update-Interval` | `SUBSCRIPTION_UPDATE_INTERVAL_HOURS` (часы). |
| `Subscription-Userinfo` | `upload=`/`download=` — трафик владельца подписки в скоупе **«за всё время» (с учётом удалённых ключей)**: та же вторая строка, что печатают Личный кабинет и карточка пользователя в админке, из того же запроса (`repositories/traffic_scope.py`, `ALL_TIME`). Удалённые ключи считаются потому, что счётчик в клиенте читается как «сколько этот аккаунт использовал», и удаление ключа не должно уводить его назад. Если для владельца ничего никогда не измерялось — часть опускается (измеренный ноль — это ответ, и он отдаётся). `expire=` — общий `expires_at` детей в unix-секундах (если бессрочно — опускается). Если нет ни того, ни другого, заголовок не отдаётся вовсе. |
| `Cache-Control` | `no-store` — тело ответа это живой набор креденшлов. |

`total=` не отдаётся **никогда**: квоты по трафику в этом деплое нет, любое число здесь было бы
выдумкой, а клиенты читают выдуманную квоту как жёсткий лимит.

## UI в боте

Всё описанное ниже появляется **только при `SUBSCRIPTION_ENABLED=true`**. При выключенном флаге
бот ведёт себя ровно как до фичи: в «Создать ключ» нет опции, в «Мои ключи» нет группы бандлов, а
callback `bundle:*`, который всё-таки пришёл (повтор, ручной ввод), отклоняется guard'ом до любого
обращения к сервисам. **Новой кнопки в главном меню нет.**

| Где | Что |
|---|---|
| **Создать ключ** | Пункт «All-in-One» рядом с VLESS / AmneziaWG / Hysteria2. После предупреждения про AmneziaWG спрашивает **вид** (базовая / расширенная, оба описаны), затем использует обычный мастер создания (заметка → срок → подтверждение). На экране результата перечислено, что реально вошло в бандл, и названы протоколы, которые не вошли из-за выключенного бэкенда. Админ создаёт бандл через этот же мастер; в админской «выдаче ключа пользователю» пункта all-in-one нет. |
| **Мои ключи** | Обычная запись списка: стоит среди ключей по дате создания и нумеруется из того же сквозного счёта, что и они. |
| **Карточка бандла** | Те же пять кнопок, что и у ключа, — Конфиг · Статистика · Отозвать · Заметка · Удалить — плюс строка о том, что AmneziaWG выдаётся **отдельным ключом**. |
| **Админ-панель → «🔗 All-in-One»** | Только superadmin: две массовые операции из [Приведение существующих подписок](#приведение-существующих-подписок). |

- **Конфиг** показывает `https://<host>[:<порт>]/sub/<token>`. Host — **не отдельная настройка**:
  это `HYSTERIA2_SNI` (с откатом на `HYSTERIA2_HOST`), потому что эндпоинт терминирует TLS копией
  того самого сертификата этого домена — так URL, сертификат и hy2-ссылки остаются на одном домене
  по построению. Порт — `SUBSCRIPTION_PUBLIC_PORT`; при `0` (только loopback) экран честно
  сообщает, что эндпоинт не опубликован, вместо нерабочей ссылки. **QR-кода нет** — в дереве
  зависимостей нет QR-библиотеки, и тащить её ради картинки этой фичи не нужно; URL отдаётся
  блоком `<code>` (тап — копирование). Токен попадает в чат и никуда больше: ни одна строка лога
  его не печатает.
- **Статистика** — сумма по бандлу **плюс разбивка по протоколам** (VLESS, Hysteria2). Источники
  разные — stats API Xray и trafficStats Hysteria2, — и любой из них может быть недоступен
  отдельно, поэтому именно разбивка позволяет атрибутировать провал (или всплеск). Поключевые
  цифры по-прежнему в одном тапе на каждом дочернем ключе.
- **Отозвать** — подтверждение, затем каскад по детям и ротация токена, так что уже выданный URL
  мёртв. **Удалить** — подтверждение, затем дети и только потом строка бандла. **Заметка**
  использует тот же мастер, что и заметка ключа.

## TLS-терминация

**TLS терминирует сам процесс** (`ssl_context` на публичном порту). Reverse-proxy в стеке нет, и
этот PR его не вводит: nginx ради одного маршрута — это ещё один привилегированный демон, ещё
одна поверхность конфигурации и ещё одна зависимость по рестартам.

- **Публичный порт** — `SUBSCRIPTION_PUBLIC_PORT` (`0` — выключен, эндпоинт только на loopback).
  TCP/443 занят Xray REALITY, TCP/8443 — MTProxy, поэтому берётся свободный порт (например,
  `2096`) и открывается трекаемым правилом (ниже).
- **Открытым текстом наружу — невозможно**: публичный порт без обеих TLS-переменных не даёт
  процессу стартовать (`Settings.validate_subscription_ready`), а loopback-хост валидируется как
  loopback-адрес.
- **Чей ключ и под кем читается** — процесс работает под непривилегированным пользователем
  **`vpn-bot`** (как и `vpn-bot-hy2-auth.service`) и читает **групп-читаемую копию уже
  выпущенного** Let's Encrypt-сертификата для домена сервера — того же, что `acme.sh` ставит для
  Hysteria2, но *не* сам `/etc/hysteria/key.pem`. Отдельная копия оставляет материал Hysteria2
  нетронутым и даёт процессу ровно один читаемый секрет:

```bash
sudo install -d -o root -g vpn-bot -m 0750 /etc/vpn-bot/tls
# Добавьте ВТОРУЮ цель в существующий вызов acme.sh --install-cert (hysteria-цель
# не трогать), чтобы обновления попадали и сюда, и укажите в --reloadcmd трекнутый
# хук раскладки — тогда новую цепочку подхватят ОБА читателя:
sudo chmod 0755 /opt/vpn-service/deploy/vpn-bot-acme-reload.sh
sudo acme.sh --install-cert -d <DOMAIN> \
  --fullchain-file /etc/vpn-bot/tls/fullchain.pem \
  --key-file       /etc/vpn-bot/tls/privkey.pem \
  --reloadcmd      "/opt/vpn-service/deploy/vpn-bot-acme-reload.sh"
```

Ключ читается **один раз при старте**, поэтому обновление подхватывается этим рестартом.
`ReadOnlyPaths` для него юниту не нужен: `ProtectSystem=strict` делает `/etc` read-only, а не
невидимым, и доступ реально ограничивают права на файл.

`deploy/vpn-bot-acme-reload.sh` — это трекнутая форма шага reload: он заново выставляет
`root:vpn-bot` / `0640` на обновлённый ключ, отдаёт Hysteria2 её собственную копию и перезапускает
**оба** сервиса — `hysteria-server` и `vpn-bot-subscription`. Запускается прямо из чекаута (как
`deploy/update-ip2asn.sh`), поэтому деплой его обновляет; в `/usr/local/sbin` он не ставится.
Прогнать вхолостую, не дожидаясь продления:

```bash
sudo /opt/vpn-service/deploy/vpn-bot-acme-reload.sh --dry-run
```

> **Известное расхождение с хостом — проверьте своё.** На хосте, поднятом до того, как этот хук
> стал трекаться, `--reloadcmd` может всё ещё указывать на написанный руками скрипт (например,
> `/usr/local/sbin/acme-reload.sh`), который копирует сертификат в Hysteria2 и перезапускает
> `hysteria-server`, но **никогда не перезапускает `vpn-bot-subscription`**. Тогда этот эндпоинт
> после каждого продления продолжает отдавать **предыдущий** сертификат, пока его не перезапустит
> что-то ещё — деплой или перезагрузка; именно поэтому проблему легко не заметить. Сначала
> прочитайте живое значение, ничего не меняя:
>
> ```bash
> sudo grep -r Le_ReloadCmd /root/.acme.sh/*/ ; sudo cat /usr/local/sbin/acme-reload.sh
> ```
>
> Переключение `--reloadcmd` на трекнутый хук (повторите команду `--install-cert` выше — она
> перезаписывает сохранённое значение) закрывает расхождение. Сделайте это **до** следующего
> продления, а не после.

## Go-live (установка drift, руками)

`scripts/deploy.sh` автоматически ставит **только** `vpn-bot.service`; как и любой другой юнит из
`deploy/`, этот печатается как drift и ставится оператором. Phase 1 дополнительно печатает
информационную строку: установлен ли юнит, активен ли он и слушаются ли настроенные порты — она
никогда не фатальна, потому что хост без этого эндпоинта — нормальное состояние, и она терпит
юнит, который поднялся, но ещё не успел забиндиться (см. [Задержка от старта до
бинда](#задержка-от-старта-до-бинда)).

**Ставится руками, но перезапускается деплоем.** Когда юнит уже установлен и активен,
`scripts/deploy.sh` в Phase 2 **перезапускает его на каждом деплое** — чтобы изменения в
`subscription_server/`, `services/key_bundles.py` или общих форматтерах ссылок реально дошли до
работающего эндпоинта. Ручного шага рестарта после деплоя больше нет. Юнит, которого нет, или
который был неактивен на момент старта деплоя, пропускается и остаётся ровно как был — деплой
по-прежнему не ставит, не enable-ит и не запускает его. Подробности и политика отказа — в
[ранбуке](operations.ru.md#деплой-перезапускает-и-sidecar-юниты).

**Порядок ниже — это и есть порядок.** TLS-материал должен существовать до того, как `.env` на
него сошлётся, а правило фаервола — до того, как порт начнёт отвечать; публичный порт без
TLS-пары вообще не стартует (следующий раздел), так что `.env` первым шагом купит только
неудачный рестарт.

```bash
# 1. Копия TLS — групп-читаемая копия уже выпущенного Let's Encrypt-сертификата
#    домена, ставится acme.sh (полная команда с --reloadcmd — в разделе выше).
sudo install -d -o root -g vpn-bot -m 0750 /etc/vpn-bot/tls
sudo acme.sh --install-cert -d <домен> \
  --fullchain-file /etc/vpn-bot/tls/fullchain.pem \
  --key-file       /etc/vpn-bot/tls/privkey.pem \
  --reloadcmd      "/opt/vpn-service/deploy/vpn-bot-acme-reload.sh"
ls -l /etc/vpn-bot/tls          # ожидаем root:vpn-bot, privkey.pem 0640

# 2. .env — флаг, порты и TLS-пара, одной правкой
#    SUBSCRIPTION_ENABLED=true
#    SUBSCRIPTION_BIND_HOST=127.0.0.1
#    SUBSCRIPTION_BIND_PORT=8445          # loopback, НЕ 8443 (занят xhttp/mtproxy)
#    SUBSCRIPTION_PUBLIC_PORT=2096        # пусто или 0 оставляет только loopback
#    SUBSCRIPTION_TLS_CERT=/etc/vpn-bot/tls/fullchain.pem
#    SUBSCRIPTION_TLS_KEY=/etc/vpn-bot/tls/privkey.pem

# 3. Фаервол (трекаемое правило — никаких `ufw allow` руками)
sudo bash deploy/ufw-subscription.sh          # порт берётся из .env
#   ... и обратно:
sudo bash deploy/ufw-subscription.sh --delete

# 4. Юнит — ставится руками (drift); deploy.sh его не ставит
sudo install -m0644 deploy/vpn-bot-subscription.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable vpn-bot-subscription

# 5. Рестарт ОБОИХ процессов — каждый читает .env один раз, при старте.
#    Это разовый рестарт на go-live; дальше `scripts/deploy.sh` перезапускает
#    эндпоинт на каждом деплое сам (см. абзац выше).
sudo systemctl restart vpn-bot-subscription vpn-bot

# 6. Подождать ~20с. Перед биндом эндпоинт импортирует рендереры ссылок, поэтому
#    сокетов после рестарта секунд двадцать просто нет (см. ниже).
sleep 25

# 7. Проверка: сокеты, затем журнал
sudo ss -tlnp | grep -E '8445|2096'         # ожидаем ОБА: loopback 8445 + публичный 2096
sudo journalctl -u vpn-bot-subscription -n 30 --no-pager
#    ожидаем: "subscription endpoint listening on 127.0.0.1:8445 ..."
#         и  "subscription endpoint listening on :2096 (HTTPS, cert=...)"

# 8. Smoke
curl -si http://127.0.0.1:8445/sub/definitely-not-a-real-token | head -1   # ожидаем 404
curl -si https://<домен>:2096/sub/definitely-not-a-real-token | head -1    # ожидаем 404 по TLS
#    затем открыть реальный sub-URL из экрана «Конфиг» в боте — ожидаем 200.
```

### Публичный порт без TLS-пары = отказ старта, и это by design

Заданный `SUBSCRIPTION_PUBLIC_PORT` без **обеих** переменных `SUBSCRIPTION_TLS_CERT` и
`SUBSCRIPTION_TLS_KEY` заставляет процесс написать в лог `subscription endpoint refuses to start:
...` и выйти с кодом `1` (`Settings.validate_subscription_ready`, вызывается из
`subscription_server.config`). При `Restart=on-failure` systemd повторяет попытки, и юнит
заканчивает в состоянии `failed`. **Это фича, а не баг**: тело ответа — полный набор клиентских
ссылок пользователя, поэтому единственная альтернатива (поднять публичный порт открытым текстом)
обязана быть недостижима правкой `.env`. Если после правки `.env` юнит не поднимается — сначала
читаем журнал: та строка прямо называет недостающую переменную.

### Задержка от старта до бинда

Процессу нужно **около 20 секунд** между `systemctl start` и захватом сокетов: перед биндом он
импортирует `services.xray` и `bot.formatters` (единственный источник правды для форматов ссылок
`vless://` и `hy2://` — они переиспользуются, чтобы ссылки в подписке были байт-в-байт теми же,
что и в per-key выдаче), а эта цепочка тянет `aiogram`, на который и приходится почти вся
стоимость.

«Чинить» это отложенным импортом **не стоит**. `XrayService` — базовый класс рендерера ссылок
(подкласс объявлен на уровне модуля, поэтому его импорт нельзя убрать внутрь функции), а
`services.xray` сам импортирует `bot.formatters` — так что отложить один только импорт
форматтеров в `subscription_server/render.py` не даст ничего. По-настоящему быстрый бинд требует
переработки общего кода рендера ссылок, а расхождение между ссылками в подписке и per-key
ссылками — не тот риск, ради которого стоит экономить 20 секунд старта.

Что из этого следует на практике:

- Сразу после рестарта `ss` не покажет ни `8445`, ни `2096` ещё ~20с. Это надо просто переждать —
  `journalctl -u vpn-bot-subscription` печатает по строке `listening on ...` в момент, когда
  соответствующий бинд состоялся.
- `scripts/deploy.sh` перепроверяет порты до `SUBSCRIPTION_BIND_WAIT` секунд (по умолчанию
  `30`), пока юнит активен, — так что деплой, попавший в медленный старт, не напишет ложное
  «NOT listening». Проверка выполняется дважды — в Phase 1 и ещё раз после рестарта в Phase 2, —
  через одну и ту же единственную реализацию этого ожидания. Проверка портов в любом случае
  информационная и **никогда** не валит деплой; фатален только один случай — юнит был активен,
  и после нашего рестарта не вернулся в `active`.
- Задержка только стартовая. На запросы она не влияет: `GET /sub/{token}` обслуживает уже
  прогретый процесс.

Переключение `SUBSCRIPTION_ENABLED` требует рестарта **обоих** юнитов — `systemctl restart
vpn-bot-subscription vpn-bot`: каждый процесс читает `.env` при старте, эндпоинт — ради маршрутов,
бот — ради UI. Флаг включается **правкой живого `.env`, а не коммитом**: дефолт в репозитории
остаётся `false`. Юнит остаётся активным в обоих случаях — с выключенным флагом он держит
loopback-сокет и просто отвечает `404`, поэтому его состояние не «мигает» вместе с флагом, — но
**публичный слушатель при выключенном флаге не поднимается вовсе**: порт, который умеет только
отдавать `404`, это поверхность атаки без пользы.
