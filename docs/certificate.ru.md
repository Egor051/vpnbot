# TLS-сертификат и DNS бота

Сертификат домена выпускает и продлевает **acme.sh** (DNS-01 через Cloudflare); раскладывает его по
сервисам, которые его читают, — **бот**: фиксированный root-helper `/usr/local/sbin/vpn-bot-cert`,
список этих потребителей записан в коде. Токен Cloudflare — бота (один на бота), DNS-записи, которые
бот держит направленными куда нужно, перечислены в его базе. На этом строятся установка протоколов из
Telegram, смена IP сервера и смена домена.

🇬🇧 English version: [certificate.md](certificate.md)

## Зачем

acme.sh хранит **один** install-cert на домен: пути, куда он копирует, и **один** `reloadcmd`. При
одном из переносов хоста этот reloadcmd указывал только на часть потребителей, и остальные
продолжали отдавать сертификат, который вот-вот истечёт. Поэтому потребители — больше не
конфигурация на хосте: это **реестр** `scripts/vpn-bot-cert` (ревью, тесты), а reloadcmd, который
acme.sh вызывает после каждого продления, — сам helper:

```bash
acme.sh --install-cert -d <domain> [--ecc] --reloadcmd "/usr/local/sbin/vpn-bot-cert deploy"
```

**без** `--cert-file` / `--key-file` / `--fullchain-file`: acme.sh ничего не пишет вне своего
каталога; `deploy` раскладывает пару сам — атомарно, потребитель за потребителем.

## Реестр потребителей

| Потребитель | Файлы (что, владелец, режим) | После обновления | Активен, когда |
|---|---|---|---|
| `hysteria` | `/etc/hysteria/cert.pem` (fullchain, `hysteria:hysteria 0644`), `/etc/hysteria/key.pem` (ключ, `hysteria:hysteria 0600`) | `systemctl restart hysteria-server`, затем он должен быть active | unit есть, `/etc/hysteria` есть, нет `/etc/vpn-bot/uninstalled/hysteria2` |
| `nginx` (self-steal REALITY на 127.0.0.1:8443) | `/etc/vpn-bot/tls/fullchain.pem`, `/etc/vpn-bot/tls/privkey.pem` (`root:vpn-bot 0640`) | `nginx -t`, затем `systemctl reload nginx` | unit есть |
| `subscription` (`:2096`, читает при старте) | те же два файла | `systemctl try-restart vpn-bot-subscription` (остановленный эндпоинт не запускается) | unit есть |

Сам `/etc/vpn-bot/tls` — `root:root 0755`. Это ровно те владельцы и режимы, которые выставляет
отслеживаемый хук `deploy/vpn-bot-acme-reload.sh` (замерены на основном сервере); тест держит их
согласованными. На хосте без группы `vpn-bot` (модель root-legacy) два TLS-файла получают группу
`root`. Статус также показывает, что каждый потребитель **настроен** читать — `tls.cert`/`tls.key`
hysteria, `SUBSCRIPTION_TLS_CERT`/`_KEY`, строки `ssl_certificate` nginx — и отмечает потребителя,
который читает то, что реестр не раскладывает. У nginx читаются `nginx.conf` и каждый файл, который
называют его директивы `include` (glob, относительно `/etc/nginx`, рекурсивно), а также `conf.d/` и
`sites-enabled/`; файл вне `/etc/nginx` и `/usr/share/nginx` (туда Debian / Ubuntu ссылаются на
сниппеты модулей) не читается никогда — он называется, а потребитель считается **непроверяемым**:
verify мастера не проходит, а не гадает, что такой потребитель отдаёт (так же для hysteria с
нечитаемым конфигом).

## `vpn-bot-cert`

| Команда | Что делает |
|---|---|
| `status [--json]` | Только чтение. Каждый домен acme.sh (SAN, срок, тип ключа, соответствует ли ключ, reloadcmd, учётные данные Cloudflare, с которыми он продлевается, — только отпечаток), домен бота (тот, чей reloadcmd — `vpn-bot-cert deploy`) или домен для принятия, каждый потребитель (установлен или почему нет, его файлы: есть ли, совпадают ли с acme.sh, владелец и режим, срок на копии), токен бота (отпечаток), строка cron и **замечания** с уровнем. Их показывают экран бота и самопроверка. Текст собственной конфигурации хоста (reloadcmd, настроенный руками, может содержать URL health-check, заголовок или API-ключ) показывается **с маскировкой**: шаблоны `utils/redact` плюс любой заголовок, `NAME=value`, `--flag value` или `curl -u` с именем учётных данных; экран маскирует его ещё раз. |
| `deploy [--domain D] [--all] [--dry-run] [--json]` | ЭТО reloadcmd (ниже). |
| `issue --names a,b --zone ZONE` | DNS-01 (`dns_cf`) с токеном бота, Let's Encrypt, тип ключа домена (`ec-256` для нового), `--force`; затем install-cert, как выше, затем deploy. Если acme.sh нет — сначала он ставится. Имя сертификата здесь поменять нельзя (это смена домена). |
| `renew --force [--zone ZONE]` | `acme.sh --renew --force` домена бота — проверить, что продление работает целиком. С токеном бота сначала сохранённые у домена `CF_Token` / `CF_Zone_ID` выставляются в него (при продлении acme.sh читает конфиг домена), и дальше cron продлевает с тем же токеном. Затем deploy. |
| `adopt [--domain D] [--dry-run]` | Миграция (ниже): домен принимается как есть, переписывается только его install-cert. Если `vpn-bot-cert deploy` называют несколько доменов, `--domain` выбирает тот, что остаётся доменом бота, Каждый **другой** домен, который ещё доходит до потребителей, **освобождается**: очищается reloadcmd, называющий helper, и каждый путь `Le_Real*` в реестр (на эти пути acme.sh копирует сам после продления, не вызывая helper); остальные его цели и собственный reloadcmd остаются. `issue` освобождает их так же, а принятый хост, на котором такой «писатель» появился руками позже, можно принять ещё раз, чтобы его освободить. |
| `act` | Проверка и действие каждого установленного потребителя на тех файлах, что у него есть, — ничего не пишется. Использует откат мастера. |

`deploy`, `issue`, `renew` и `adopt` принимают `--expect-pair SHA` (16 hex из `pair_sha` статуса) —
пару, на которой запуск был спланирован. Если к началу запуска у acme.sh уже другая пара (cron
продлил между планом и подтверждением), запуск отклоняется, ничего не изменено: план его больше не
описывает. `deploy` сравнивает ту самую пару, которую раскладывает; остальные проверяют после
ожидания работающего acme.sh, под lock, до того как тронуты acme.sh или конфиг. `issue` и `adopt`
принимают ещё `--expect-release DIR[,DIR…]` (`""` — ни одного): каталоги доменов, которые план
освобождает, — отказ так же, если этот набор изменился (мастер сделал бэкап именно их).

Коды выхода: 0 — ок; 1 — потребитель не поднялся, его группа откатена; 2 — использование; 3 — отказ
(нечего принимать, нет токена, плохая пара, другой домен, пара не та, что в плане); 5 — не могу
(инструмент или файл).

### `deploy`: атомарно, по группам

1. **Источник** — собственная пара acme.sh этого домена: `fullchain.cer` + `<domain>.key` в
   `/root/.acme.sh/<domain>[_ecc]/`. Домен — тот, что называет acme.sh (`Le_Domain` и рабочий
   каталог, из которого он запускает reloadcmd), иначе принятый. Пара сначала проверяется `openssl`:
   ключ соответствует сертификату (тот же открытый ключ), сертификат не истёк, его SAN покрывает имена
   домена. Плохая пара останавливает всё до того, как тронут хоть один файл.
2. Потребители с общим файлом — **одна группа** (`nginx` + `subscription`; `hysteria` отдельно).
3. В каждой группе изменённый файл пишется **рядом** с целевым (`.<name>.vpn-bot-cert-new`, тот же
   каталог, владелец и режим выставляются до данных), и подготовленная пара ещё раз проверяется
   `openssl` — так, как её прочитает потребитель. Затем старая копия сохраняется
   (`.<name>.vpn-bot-cert-old`), и новые файлы переименовываются поверх старых, подряд.
4. Действия группы. Неудачное действие — или unit, не active после рестарта, — **возвращает этой
   группе прежние файлы** и выполняет её действия заново на них. Остальные группы остаются на новой
   паре. Код выхода 1.
5. Действие выполняется только для потребителя, чьи файлы изменились, или если
   `/var/lib/vpn-bot-cert/state.json` говорит, что его последнее действие было на другой паре
   (`--all` — для каждого установленного). Неверный владелец или режим чинится без рестарта.

Откатанный потребитель остаётся на старом (ещё действующем) сертификате, а acme.sh не продлевает
снова 60 дней. Статус показывает это сразу (копия отличается от acme.sh, красное — если до истечения
меньше 7 дней), ежедневная самопроверка присылает сигнал, а «📦 Разложить заново» — или следующее
продление — разложит её снова.

У acme.sh нет своего lock, а его cron (`acme.sh --cron` в crontab root) не берёт lock
`vpn-bot-cert`. Поэтому, пока собственный acme.sh helper'а работает с доменом (`issue` / `renew` /
`adopt`), `Le_NextRenewTime` этого домена сдвинут на час вперёд — `acme.sh --cron` продлевает
только домен, которому пора, и запуск cron в это время его пропускает, — а потом возвращается
прежним, если acme.sh не записал новое. Затем helper ждёт (до 5 минут, потом отказ) acme.sh,
который уже работал. Вместе: нет момента, когда cron и helper меняют один домен сразу, и crontab
root не переписывается. `deploy` продления по cron ждёт lock helper'а.

Когда acme.sh запускает reloadcmd изнутри `issue` / `renew` / `adopt` (переменная окружения
`VPN_BOT_CERT_NESTED` называет lock, который держит родитель), `deploy` уступает: родитель
раскладывает сам сразу после acme.sh, со своим отчётом.

## Токен Cloudflare: один на бота

Один файл — `/etc/vpn-bot/dns_failover/cloudflare_token` (0600, владелец — пользователь бота): им
режим фолбэка переключает свои имена, им бот пишет свои DNS-записи, его `vpn-bot-cert` передаёт
acme.sh для DNS-01 — как `CF_Token` в окружении acme.sh, никогда в командной строке. Вводится только
в боте («🔑 Токен Cloudflare» или «🔑 Токен DNS API» режима фолбэка — тот же файл, та же проверка):
сообщение **удаляется** сразу после чтения. Права токена: **«Zone · Zone · Read»** и **«Zone · DNS ·
Edit»** на зону — бот и `vpn-bot-cert` находят зону по имени (`GET /zones?name=`, для этого нужно Zone
Read), поэтому токен только с DNS Edit отклоняется на шаге 2. До сохранения бот проверяет токен через
API (`services/dns.py`):

1. `GET /user/tokens/verify` — активен;
2. ему видна зона имён, введённых для «🆕 Выпустить» (иначе — имени сертификата, иначе — `HYSTERIA2_SNI`); на чистом хосте без того и другого имена сначала вводятся;
3. он читает её записи;
4. TXT-запись `_vpn-bot-token-check.<зона>` создаётся **и удаляется** — единственное доказательство
   «Zone · DNS · Edit», которое Cloudflare даёт токену без права читать собственные права (DNS-01
   делает ровно это).

Токен, не прошедший шаг, отклоняется с причиной этого шага, ничего не сохраняется. В аудите — только
отпечаток (8 hex от sha256), никогда не значение. Статус показывает, продлевает ли acme.sh с тем же
токеном (по отпечаткам), а «🔄 Проверить продление» переключает acme.sh на него. Токен могут
заменить, пока идёт продление (а id зоны — это запрос к Cloudflare): `vpn-bot-cert` перечитывает
файл после этого запроса и ещё раз после записи конфига acme.sh и записывает более новый токен
следующим проходом — в конфиге в итоге тот токен, что лежит в файле (если токен всё меняется, после
трёх проходов запуск отклоняется, а не пишет его наполовину).

Все имена сертификата должны быть в одной зоне (`CF_Zone_ID` — одна зона): выпуск и продление
отказывают на имени из другой зоны ещё при сборке запуска, до плана. Для `issue` бот передаёт
**имя** зоны; `vpn-bot-cert` спрашивает у Cloudflare её id тем же токеном
(`GET /zones?name=`) и отдаёт acme.sh `CF_Zone_ID` — id зоны, оставленный в `account.conf` acme.sh
другой настройкой, не используется никогда. (Сам id дальше не передаётся: 32 hex-символа любая
редакция секретов маскирует, включая сохранённые параметры мастера.)

## DNS-записи, которыми владеет бот

`dns_records` (схема v48) — **один** список A-записей, которые держит бот: имя, назначение
(`fallback_origin` — upstream hub, всегда IPv4 основного сервера; `host` — имя этого сервера),
последний записанный адрес, id в Cloudflare и была ли запись до того, как бот её взял (`adopted`).
Каждая запись идёт через `DnsService.write_a`: единственная A-запись имени получает адрес,
**`proxied=false`**, TTL 60 — какой бы запись ни была (проксируемая запись увела бы VPN за
HTTP-прокси Cloudflare). Несколько A-записей или (если вызывающий так сказал) запись на неожиданный
адрес — отказ, ничего не пишется. `delete_a` удаляет только запись, которой бот владеет **и которую
создал сам**; принятая теряет владение и остаётся в Cloudflare; имя, которым бот не владеет, —
отказ.

origin режима фолбэка раньше хранился только неявно (upstream hub). Теперь это строка: «🛟 Сделать
hub» пишет её через `upsert_a(purpose="fallback_origin")`, а миграция v48 переносит origin
существующего hub (`adopted`: база никогда не записывала, создал ли её бот). Набор переключения
(`failover_names`) владением **не** является: эти имена — собственный домен сервера, бот меняет их
адрес через тот же `write_a`, но никогда их не создавал и не удаляет.

## «🔐 Сертификат и DNS» в мастере

Экран (SUPERADMIN): сертификат (имя, ключ, до какого числа, сколько дней, SAN), reloadcmd
(✅ `vpn-bot-cert deploy` / 🟡 старый хук / 🔴 что-то другое), acme.sh и его строка cron, каждый
потребитель, токен (и продлевает ли с ним acme.sh), DNS-записи бота и замечания. Кнопки:

| Кнопка | Запуск режима `cert` |
|---|---|
| «🔁 Принять текущий сертификат» — только до принятия; «🔁 Принять <домен>», по кнопке на домен, если сертификатом бота может быть любой из нескольких доменов acme.sh — в том числе если `vpn-bot-cert deploy` уже называют несколько (план перечисляет освобождаемые) | `action=adopt` (`names` — выбранный домен) |
| «🆕 Выпустить / перевыпустить» → «▶️ Составить план» («✏️ Другие имена» — ввести свои) | `action=issue`, `names`, `zone` |
| «🔄 Проверить продление» — после принятия | `action=renew` (`zone` при токене бота) |
| «📦 Разложить заново» — если копия потребителя отличается, не была принята им или у неё не тот владелец / режим | `action=deploy` |
| «🔑 Токен Cloudflare» | — (задать / удалить, TOTP) |

Каждый запуск — по контракту мастера ([wizard.ru.md](wizard.ru.md)): план с diff (строки конфига
acme.sh до → после, сертификат до → после, каждый потребитель и что с ним будет), TOTP,
«✅ Применить», затем apply (отказ, если пара acme.sh уже не та, на которой составлен план, или с тех
пор другой домен начал или перестал доходить до потребителей, — helper получает и то и другое как
`--expect-pair` / `--expect-release`; бэкап каталога домена acme.sh — и каждого домена, который запуск
освобождает, — файлов каждого потребителя и state, затем helper) → verify (`vpn-bot-cert status`: домен — бота, reloadcmd наш, своих путей у acme.sh нет, пара
действует 7+ дней и покрывает имена, каждый установленный потребитель держит пару, выполнил на ней
действие и настроен читать файлы реестра, а не свою пару; hysteria, чей конфиг не прочитать, — тоже
не проверен; для issue / renew — НОВАЯ пара) → rollback при сбое (бэкап восстанавливается — домен,
созданный запуском, убирается в сторону, чтобы acme.sh его не продлевал, — затем
`vpn-bot-cert act`). Один глобальный lock (мастера), журнал аудита (`wizard_*`, `dns_*`). Сеть хоста
ни один шаг не меняет — dead-man не нужен. Режим запускает `vpn-bot-cert` в собственной группе
процессов с бюджетом 2400 с (ожидание работающего acme.sh, собственные 900 с acme.sh, установка
acme.sh, действие каждого потребителя) внутри таймаута apply режима — 2700 с; по таймауту вся группа —
`vpn-bot-cert` и запущенный им acme.sh — убивается до начала отката (helper так же поступает с каждой
своей командой), поэтому откат никогда не восстанавливает файлы под ещё идущим продлением.

Каталоги rsa и ecc с одним именем: тот, из которого acme.sh запустил helper, иначе тот, что уже домен
бота, иначе настроенный руками для потребителей, иначе тот, чья пара годна (ecc — только если после
этого остаются оба). План называет каталог, с которым работает.

## Миграция прода: принятие (adoption)

Домен acme.sh основного сервера настроен вручную: `Le_RealFullChainPath` / `Le_RealKeyPath` =
`/etc/vpn-bot/tls/…`, reloadcmd пустой, отслеживаемый хук или часть потребителей. **Принятие** берёт
его как есть:

1. Задеплойте этот релиз. Для acme.sh ничего не меняется: продление до шага 2 работает как сейчас.
2. «🧙 Мастер настройки → 🔐 Сертификат и DNS» показывает домен как кандидата на принятие и замечание
   («reloadcmd …»). «🔁 Принять текущий сертификат» → план показывает diff:

   ```
   - Le_RealKeyPath='/etc/vpn-bot/tls/privkey.pem'
   + Le_RealKeyPath=''
   - Le_RealFullChainPath='/etc/vpn-bot/tls/fullchain.pem'
   + Le_RealFullChainPath=''
   - Le_ReloadCmd='<что было>'
   + Le_ReloadCmd='/usr/local/sbin/vpn-bot-cert deploy'
   ```

   и для каждого потребителя — уже ли его копия совпадает с парой acme.sh (тогда ничего не
   перезапускается) или нет (тогда он получает пару и своё действие — ровно тот потребитель, которого
   пропускал старый reloadcmd).
3. «✅ Применить»: `acme.sh --install-cert -d <domain> [--ecc] --reloadcmd "/usr/local/sbin/vpn-bot-cert deploy"`
   (acme.sh сохраняет все `Le_Real*` пустыми и один reloadcmd), затем deploy. Сертификат **не**
   перевыпускается. verify, иначе rollback.
4. По желанию — задайте токен бота («🔑 Токен Cloudflare») и запустите «🔄 Проверить продление»:
   дальше acme.sh продлевает с токеном бота. Let's Encrypt выдаёт не больше 5 сертификатов на одни и
   те же имена в неделю.

Отслеживаемый хук `/usr/local/sbin/acme-reload.sh` остаётся установленным и неизменным для ещё не
принятого хоста (его продления работают как прежде); статус показывает его 🟡 до принятия.

Вернуться к прежней настройке (откат релиза этого не требует: более старый релиз оставляет
`/usr/local/sbin/vpn-bot-cert` на месте, и принятый reloadcmd продолжает работать):

```bash
sudo /root/.acme.sh/acme.sh --install-cert -d <domain> --ecc \
  --fullchain-file /etc/vpn-bot/tls/fullchain.pem --key-file /etc/vpn-bot/tls/privkey.pem \
  --reloadcmd /usr/local/sbin/acme-reload.sh
```

## Самопроверка

Пункт `certs` «🩺 Самопроверки» — это `vpn-bot-cert status --json`: по пункту `cert:<key>` на каждое
замечание (красное / жёлтое), зелёный `certs`, если замечаний нет. Красное: меньше 7 дней (и на
устаревшей копии потребителя), reloadcmd — ни `vpn-bot-cert deploy`, ни старый хук, нет строки
`--cron` acme.sh, другой домен acme.sh копирует поверх файлов реестра, ключ пары не соответствует.
Жёлтое: меньше 21 дня, старый хук (примите сертификат), копия потребителя отличается или не тот
владелец / режим, потребитель читает файлы, которые реестр не раскладывает, acme.sh продлевает с
другим токеном, нет токена бота. Без helper'а (хост ещё не задеплоен) работает прежняя проверка по
файлам.

## Установка acme.sh

`issue` на хосте без acme.sh ставит релиз **3.1.1**: `acme.sh` и `dnsapi/dns_cf.sh` с
`raw.githubusercontent.com/acmesh-official/acme.sh/3.1.1/`, каждый сверяется с закреплённым sha256
(другая копия отклоняется), затем `acme.sh --install` (вместе с cron) и
`--set-default-ca --server letsencrypt`.

## Где что лежит

| Путь | Что |
|---|---|
| `/usr/local/sbin/vpn-bot-cert` | root-helper (`OUT_OF_REPO_HELPERS`, required на main; `INSTALL_HELPERS`) |
| `/usr/local/sbin/vpn-bot-wizard-cert` | режим мастера |
| `/var/lib/vpn-bot-cert/state.json` | какую пару каждый потребитель принял последней (root 0644) |
| `/run/vpn-bot-cert.lock` | одно изменение за раз (cron acme.sh и мастер ждут друг друга) |
| `/etc/vpn-bot/dns_failover/cloudflare_token` | токен бота (0600, пользователь бота) |
| `dns_records` | DNS-записи, которыми владеет бот |

В модели helper-nonroot бот читает статус через одну строку sudoers
(`deploy/sudoers.d/vpn-bot.example`): `/usr/local/sbin/vpn-bot-cert status --json` — и больше ничего.

Тестовый шов: `VPN_BOT_CERT_SELFTEST=1` требует `--root` (каждый путь хоста — под ним), запускает
только заглушки из `VPN_BOT_CERT_SELFTEST_BIN` (или абсолютный путь под `--root`) и хранит владельцев
в отдельном файле вместо `chown`; deploy.sh гоняет тесты от root на боевом хосте.
