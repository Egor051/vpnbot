# Relay (ключи «через relay»)

**Relay** — второй вход на этот сервер: небольшой VPS (здесь — в России), который
форвардит клиентский трафик на L4 на основной сервер. Ключ «через relay» — обычный
ключ, ссылка которого указывает на relay вместо основного хоста. Relay может быть
**несколько**; они управляются в админ-панели бота (**🛡 Админ-панель → 🛰 Управлять
relay**) и хранятся в таблице `relays` в `vpn.db`. Пока в таблице нет ни одного relay,
функция не видна.

## Топология

```
клиент ──TCP+UDP/443──▶ relay (RU VPS)
                          nftables DNAT tcp+udp dport 443 → <основной сервер>:443
                                         │
                                         ▼
                 основной сервер :443 ── xray vless-in (REALITY)
                                         ├─ XHTTP fallback → vless-xhttp-reality
                                         └─ (UDP) hysteria2
```

- Relay меняет только адрес назначения (DNAT) и маскарадит источник, поэтому
  основной сервер видит каждое подключение через relay как пришедшее с **egress-IP
  relay**. PROXY protocol нет — реальный адрес клиента до сервера не доходит.
- Клиент через relay попадает в **те же inbound'ы**, что и прямой: VLESS (TCP) и все
  профили VLESS (HTTP) на vless-in :443, Hysteria2 на UDP/443. На основном сервере
  про relay не знает ничего.
- Сам relay-хост (таблица nftables, `ip_forward`, его systemd-unit) разворачивается **из
  этого репозитория** тем же `scripts/redeploy.sh` в роли хоста `NODE_ROLE=relay` — см.
  [Relay-хост](#relay-хост-node_rolerelay).

### DNS — указывайте имя, а не адрес

Заведите DNS-имя на relay — например, `relay.anycastedge.net` — в Cloudflare **без
проксирования** (DNS only, серое облако): HTTP-прокси Cloudflare не пропускает ни
REALITY, ни QUIC. Это имя и указывайте как **host** relay.

Это важно, потому что ссылка одиночного ключа содержит host как есть. Если host — имя,
переезд relay на новый IP — это смена A-записи, и переимпортировать ключи не нужно.
Если host — IPv4-адрес, его смена в панели сразу перенаправляет **подписки** (они
рендерятся на каждый запрос), но каждый **одиночный relay-ключ**, импортированный
пользователем ссылкой, хранит старый адрес и требует переимпорта — при смене host
панель показывает, сколько таких ключей.

## Relay-хост (`NODE_ROLE=relay`)

На relay-хосте работает **одно**: `vpn-relay.service` — oneshot-unit, который выполняет
`/usr/local/sbin/vpn-relay-apply apply`. Хелпер рендерит таблицу nftables `ip vpnrelay` из
`.env` relay, применяет её **одной атомарной транзакцией `nft -f`** (`table ip vpnrelay` +
`delete table ip vpnrelay` + новая таблица — nft применяет всё целиком или оставляет прежнюю
таблицу как была) и затем ставит `net.ipv4.ip_forward = 1` (в рантайме и в
`/etc/sysctl.d/90-vpn-relay.conf`).

Больше ничего из репозитория там не работает: ни `vpn-bot`, ни `vpn-bot-subscription`, ни
`hy2_auth`, ни БД, ни Xray, AmneziaWG, WARP, и **никакого Telegram** — тот же `BOT_TOKEN` на
втором хосте конфликтовал бы с основным ботом за `getUpdates`. `config/settings.py` не
загружается, у relay свой минимальный `.env`. Собственные INPUT/OUTPUT relay (SSH на :22) не
трогаются никогда: в ruleset нет hook `input`/`output` (закреплено тестами), а drop-in sshd
вроде `/etc/ssh/sshd_config.d/00-vpnrelay-keyonly.conf` деплоя не касается.

Для портов по умолчанию отрендеренный ruleset ровно тот, что работал на relay, собранном
вручную:

```
table ip vpnrelay
delete table ip vpnrelay
table ip vpnrelay {
  chain pre {
    type nat hook prerouting priority dstnat; policy accept;
    iifname "eth0" tcp dport 443 counter dnat to <upstream>:443
    iifname "eth0" udp dport 443 counter dnat to <upstream>:443
  }
  chain post {
    type nat hook postrouting priority srcnat; policy accept;
    oifname "eth0" ip daddr <upstream> ct status dnat counter masquerade
  }
  chain relayfwd {
    type filter hook forward priority filter; policy drop;
    tcp flags syn tcp option maxseg size set rt mtu
    ct state established,related accept
    ct status dnat ip daddr <upstream> accept
    counter
  }
}
```

Каждый пробрасываемый порт получает одно правило DNAT на **тот же** порт upstream; masquerade,
MSS clamp и forward-цепочка (policy drop, проходят только DNAT'нутые потоки и ответы на них)
от портов не зависят. Flowtable и прочий тюнинг не нужны: на relay с 1 vCPU 107 Мбит/с
форварда оставляли CPU простаивающим на 96–98 %.

### `.env` relay

`/opt/vpn-service/.env` из [`deploy/relay/relay.env.example`](../deploy/relay/relay.env.example).
Читается тем же sed-парсером, которым `deploy.sh` читает `NODE_ROLE` (а fwmark-хелпер
Hysteria2 — `HYSTERIA2_PORT`): необязательный `export`, пробелы вокруг `=`, кавычки,
комментарии `# …` в конце строки, побеждает **последнее** присваивание, пустое значение
равно отсутствующему.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `NODE_ROLE` | `main` | `relay` на relay-хосте. Любое другое значение отвергается до каких-либо изменений. |
| `RELAY_UPSTREAM_IPV4` | — (обязательна) | IPv4 основного сервера. |
| `RELAY_FORWARD_TCP_PORTS` | `443` | Через запятую, 1..65535; каждый пробрасывается 1:1. |
| `RELAY_FORWARD_UDP_PORTS` | `443` | То же для UDP (Hysteria2). |
| `RELAY_WAN_IFACE` | интерфейс IPv4 default route | WAN-интерфейс правил DNAT/masquerade. Без неё хелпер отказывает, если default route нет или он уходит через несколько интерфейсов. |
| `RELAY_CHECK_SNI` | — | Если задана (и 443 пробрасывается), `vpn-relay-apply check` дополнительно делает TLS-handshake к upstream с этим SNI и **проверяет сертификат**. Укажите `XRAY_SNI` основного сервера: REALITY отдаёт незнакомого клиента своему decoy, чей сертификат валиден для этого имени. |

### `vpn-relay-apply`

| Команда | Что делает |
|---|---|
| `apply` | Рендер + атомарное применение таблицы, затем `ip_forward=1`. Это запускает unit. |
| `check` | Только чтение: живая таблица совпадает с рендером (счётчики не сравниваются; при расхождении печатается diff), `ip_forward=1`, TCP-connect к upstream на **каждый** пробрасываемый TCP-порт и TLS-handshake, если задан `RELAY_CHECK_SNI`. Им заканчивается каждый деплой. |
| `check --dry-run` | Проверить `.env` и отрендерить; под root ещё `nft -c` (проверка синтаксиса, ничего не применяется). Это запускает Phase 1 деплоя из checkout. |
| `show` | Напечатать отрендеренный ruleset. |

Коды выхода: `0` ok · `2` использование · `3` неверное/отсутствующее значение в `.env` · `4`
не определён WAN-интерфейс · `5` не root / нет утилиты · `6` nft отверг ruleset (живая таблица
не изменилась) · `7` не удалось выставить ip_forward / записать sysctl-файл · `10` таблицы нет ·
`11` живая таблица отличается от рендера · `12` ip_forward не равен 1 · `13` upstream не
отвечает на пробрасываемом TCP-порту · `14` TLS-handshake не прошёл. `check` сообщает обо всех
сбоях и выходит с кодом первого.

### Что делает `scripts/redeploy.sh` на relay

Те же команды, что на основном сервере; `deploy.sh` читает `NODE_ROLE` и отказывает хосту,
сервисы которого противоречат роли (роль `relay`, а активен `vpn-bot` или `xray`; роль `main`,
а активен `vpn-relay` и unit'а `vpn-bot` нет вовсе).

- **Phase 1** (только чтение; `CHECK=1` на ней останавливается и печатает отчёт): fetch
  `origin/main`, тот же гейт ruff / compileall / pytest на checkout, что и на основном
  сервере (тестовый venv собирается в `/var/lib/vpn-bot-deploy/`, поэтому relay нужен
  `python3-venv` и ~1 ГиБ свободного места), `vpn-relay-apply check --dry-run` из checkout,
  исходное состояние relay, сравнение установленного unit'а с
  `deploy/relay/vpn-relay.service` и `check` из checkout против живого relay — на relay, где
  ещё работает ruleset, собранный вручную, **PASS** здесь доказывает, что репозиторий
  воспроизводит его 1:1.
- **Phase 2**: бэкап живого `nft list table ip vpnrelay`, установленного хелпера, unit'а и
  sysctl-файла (`/var/backups/vpn-bot/backup-relay-<sha>-<ts>.tar.gz`; ради бэкапа ничего не
  останавливается); `git reset --hard origin/main`; установка `vpn-relay-apply` через
  `OUT_OF_REPO_HELPERS` (роль `relay`) и `deploy/relay/vpn-relay.service` как есть;
  `daemon-reload`, `enable`, `restart vpn-relay` (установленные потоки сохраняют NAT в
  conntrack на миллисекундный разрыв); проверка `vpn-relay-apply check`.
- **Любой сбой** откатывает: прежний checkout, хелпер, unit и sysctl-файл (или их отсутствие),
  сохранённая таблица применяется заново одной транзакцией, восстанавливаются enabled/active
  unit'а и прежний `ip_forward`. Деплой выходит с ненулевым кодом и отчётом об откате.
- Unit, установленный вручную и загружающий `/etc/vpn-relay.nft`, — **ожидаемый первый
  переход**, а не drift. После первого успешного деплоя `/etc/vpn-relay.nft` переименовывается
  в `/etc/vpn-relay.nft.pre-repo.<ts>` (не удаляется) и больше никем не читается.

### Новый relay с нуля

На relay (Ubuntu 24.04, root по SSH-ключу):

```bash
apt-get update && apt-get install -y git python3-venv nftables
```

```bash
git clone https://github.com/Egor051/vpnbot.git /opt/vpn-service
```

```bash
install -m 0600 -o root -g root /opt/vpn-service/deploy/relay/relay.env.example /opt/vpn-service/.env
```

Отредактируйте `/opt/vpn-service/.env`: `RELAY_UPSTREAM_IPV4` = IPv4 основного сервера и
желательно `RELAY_CHECK_SNI` = `XRAY_SNI` основного сервера. Затем проверка и деплой:

```bash
cd /opt/vpn-service && sudo CHECK=1 bash scripts/redeploy.sh
```

```bash
cd /opt/vpn-service && sudo FORCE=1 bash scripts/redeploy.sh
```

`FORCE=1` — только в этот первый раз: свежий clone уже стоит на `origin/main`, и обычный
запуск ответит «nothing to deploy» — ровно как на основном сервере. Дальше обновления
обычные: `sudo CHECK=1 bash scripts/redeploy.sh`, затем `sudo bash scripts/redeploy.sh`.

Проверка: `systemctl status vpn-relay`, `nft list table ip vpnrelay`,
`/usr/local/sbin/vpn-relay-apply check`.

Затем на **основном сервере**:

1. A-запись DNS для relay — например, `relay2.anycastedge.net` → IPv4 relay — в Cloudflare
   **без проксирования** (см. [DNS](#dns--указывайте-имя-а-не-адрес)).
2. **🛡 Админ-панель → 🛰 Управлять relay → Добавить relay**: host = это имя, source IPs =
   egress-IPv4 relay (у DNAT-relay обычно тот адрес, по которому к нему приходят), name и
   label — как в [Управлении relay](#управление-relay-в-админ-панели). (`RELAY_HOST` /
   `RELAY_SOURCE_IPS` в `.env` основного сервера с переездом relay в панель — legacy: они лишь
   один раз заполняют пустую таблицу `relays`.)
3. **«Проверить сейчас»** в карточке relay: health-проба проходит через DNAT relay до
   основного inbound'а и обратно.

Изменение `RELAY_FORWARD_*` (или любого значения в `.env` relay) не двигает `HEAD`, поэтому
применяйте его через `sudo FORCE=1 bash scripts/redeploy.sh` — с бэкапом, рестартом,
проверкой и откатом, — а не голым `systemctl restart vpn-relay`.

### Проброс порта подписки (2096) через relay

В этом релизе не сделано; что для этого нужно:

- **На relay** — простая половина: `RELAY_FORWARD_TCP_PORTS=443,2096` и
  `sudo FORCE=1 bash scripts/redeploy.sh`. TCP/2096 тогда доходит до subscription-endpoint
  основного сервера, а `check` проверяет ещё и `<upstream>:2096`.
- **На основном сервере** — часть, требующая кода:
  - URL подписки, который получает пользователь, строится на основном домене
    (`https://<HYSTERIA2_SNI>:<SUBSCRIPTION_PUBLIC_PORT>/sub/<token>`); чтобы скачивать
    подписку через relay, нужен URL с host relay, то есть отдельный URL подписки на relay в
    боте;
  - TLS терминируется на основном сервере сертификатом основного домена, значит имя relay
    должно быть в этом сертификате (SAN; раз relay пробрасывает 443 на основной сервер,
    практичнее выпускать через DNS-01);
  - rate limit endpoint'а считается по адресу пира, а каждый запрос через relay приходит с
    egress-IP relay — все пользователи relay делили бы один bucket
    (`SUBSCRIPTION_RATE_LIMIT_BURST` за `SUBSCRIPTION_RATE_LIMIT_SECONDS`), если source IPs
    relay не получат отдельной обработки;
  - правило firewall из `deploy/ufw-subscription.sh` relay уже пропускает (оно не ограничено
    по источнику), а монитор доступности по-прежнему проверял бы только `XRAY_PUBLIC_PORT`.

## Управление relay в админ-панели

Только для SUPERADMIN. **🛡 Админ-панель → 🛰 Управлять relay** показывает список relay:
метка, имя, host, вкл/выкл, «в подписках», число активных ключей и результат последней
health-пробы.

**Добавить relay** — мастер из четырёх шагов; каждое значение проверяется теми же
функциями, что раньше проверяли `.env` (неверное значение объясняется, и шаг
повторяется):

1. **имя** — `^[a-z0-9][a-z0-9-]{0,31}$`, например `ru1`. Оно записывается в каждый ключ
   этого relay (`vpn_keys.relay`) и **не меняется никогда**. Имя, которое ещё хранит
   хотя бы одна строка ключа — в любом статусе, включая удалённые, — нельзя дать новому
   relay: эти ключи молча начали бы указывать на другой хост.
2. **host** — DNS-имя (рекомендуется) или IPv4; IPv6 не принимается.
3. **source IPs** — egress-адреса relay (IPv4 / CIDR), как их видит этот сервер, через
   запятую, не пусто. Если host — IPv4-адрес, шаг предлагает кнопку «Как host».
4. **метка** — маркер в названии ключа, `^[a-z0-9-]{1,16}$`, у каждого relay своя; шаг
   предлагает `relay`, пока она не занята другим relay.

Перед созданием показывается итоговая карточка.

**Карточка relay** позволяет изменить host, source IPs, метку и заметку, включить/
выключить relay и «в подписках», запустить **«Проверить сейчас»** (та же health-проба,
один раз — результат и время остаются на карточке) и удалить relay. Каждое изменение
пишется в аудит со значениями до и после и **действует со следующей отрендеренной
ссылки**:

- бот держит в памяти снимок таблицы, который каждая запись через панель сразу
  заменяет (бот — единственный, кто пишет);
- endpoint подписок (`vpn-bot-subscription`) читает таблицу **на каждый запрос** через
  своё read-only соединение, поэтому изменение видно без рестарта.

После смены host карточка сообщает, что подписки уже указывают на новый адрес, и
сколько одиночных relay-ключей нужно переимпортировать. Если новый host — IPv4-адрес,
которого нет в source IPs, предлагается добавить его (DNAT-relay обычно отправляет
трафик с того же адреса, на который к нему приходят).

### Выключение relay

- **выкл** (`enabled=0`): ссылки его ключей отклоняются (`RelayUnavailable`, бот
  показывает ошибку вместо ссылки), его участники пропускаются в подписках (WARNING в
  логе; прямые участники отдаются как обычно), его не предлагают для новых ключей и
  подписок. Его source IPs **по-прежнему исключаются** из детектора аномалий — клиенты
  могут быть ещё подключены. Включение возвращает всё как было.
- **не в подписках** (`in_subscriptions=0`): новые all-in-one не получают участников
  через этот relay; одиночные ключи через него можно выдавать, пока он включён.
  Существующие подписки сохраняют своих участников.

### Удаление relay

- **Ключей нет** (кроме статуса `deleted`): одно подтверждение — и relay удалён.
- **Ключи есть**: экран показывает, сколько их (и сколько из них — в скольких
  подписках), и предлагает:
  - **Удалить ключи и relay** — каждый ключ через этот relay удаляется **тем же путём,
    что и с экрана ключа** (клиент Xray снимается, трафик архивируется, пишется
    аудит). Ребёнок подписки удаляется из неё, сама подписка остаётся с остальными
    участниками. Первый ключ, который не удалось удалить, останавливает всё: relay
    остаётся, а экран показывает, сколько ключей удалено, какой не удалился и почему.
    Повторный запуск продолжает с оставшихся ключей.
  - **Отключить вместо удаления** — relay выключается, ничего не удаляется.
  - **Отмена**.

Строка relay удаляется, только если в этот момент её имя не носит ни один ключ (одним
SQL-выражением), поэтому ключ, выданный во время удаления, не останется без relay.

## Переход с `.env` (`RELAY_*`)

Раньше relay настраивался переменными `RELAY_ENABLED`, `RELAY_NAME`, `RELAY_HOST` и
`RELAY_SOURCE_IPS`. Теперь они **больше не источник истины**:

- При старте бота, если таблица `relays` **пуста**, а в `.env` `RELAY_ENABLED=true` с
  `RELAY_HOST` и `RELAY_SOURCE_IPS`, этот relay создаётся один раз — имя `RELAY_NAME`
  (по умолчанию `ru1`, ровно то, что уже записано в relay-ключах), метка `relay`,
  включён, в подписках — и в лог пишется строка INFO.
- Во всех остальных случаях, если задана хоть одна из этих переменных, бот пишет
  `WARNING RELAY_* в .env игнорируются: relay управляется из админки`.
- Переменные по-прежнему разбираются так же строго: мусор (неверный host, неверный
  source IP, `RELAY_ENABLED=true` без host или source IPs) останавливает старт с
  `SettingsError`.

Порядок: задеплоить, убедиться, что relay появился в панели, затем удалить строки
`RELAY_*` из `.env`. `RELAY_HEALTH_INTERVAL` и `SERVER_FLAG_EMOJI` остаются в `.env`.

> Если на момент обновления relay-ключи были, но стоял `RELAY_ENABLED=false`, ничего
> не переносится, и эти ключи остаются отклонёнными. Их имя уже записано в ключах,
> поэтому вручную в панели его не создать: запустите бот один раз с
> `RELAY_ENABLED=true` (и прежними host/source IPs), чтобы перенести relay, и при
> необходимости выключите его в панели.

## Что такое relay-ключ

Relay — **атрибут ключа** (`vpn_keys.relay`, `NULL` у прямого ключа, иначе `name`
relay), а не новый тип ключа или транспорт:

- он создаётся тем же путём, что и прямой ключ, и получает свои uuid / secret /
  метку с обычным префиксом (`xray_tcp_*`, `xray_http_<профиль>_*`, `hy2_*`), поэтому
  `hy2_auth`, reconcile Xray (`XRAY_MANAGED_LABEL_RE`), статистика трафика и схема
  email-меток не затронуты;
- его ссылка отличается от ссылки прямого ключа ровно в двух местах: **хост** (host
  relay вместо `XRAY_PUBLIC_HOST` / `HYSTERIA2_HOST`) и **название** (метка relay
  после метки ключа: `<метка>_<метка relay>_<флаг|кружок>`, например
  `xray_tcp_ab12c_relay_🇫🇮`). Порт, REALITY `sni`/`pbk`/`sid`/`spx`/`fp`, `flow`,
  `path`/`mode`/`extra` XHTTP и `sni` Hysteria2 — те же: relay форвардит 1:1, и TLS
  по-прежнему терминируется на основном сервере его сертификатом / ключами REALITY;
- хост выбирается в одном месте (`services.relay.relay_link_host`) для всех путей —
  экран конфига, QR, мастер создания, кэш `public_payload.link`, подписка. Ключ, чей
  relay выключен, удалён или неизвестен, **отклоняется** (`RelayUnavailable`) и
  никогда не перенаправляется молча на основной хост: ссылка, которая тихо обходит
  выбранный пользователем relay, — ровно та ошибка, от которой это защищает.

Пользователь выбирает это в мастере создания: после шага протокола (и профиля XHTTP),
пока включён хотя бы один relay, бот спрашивает **«Как подключаться?»** с кнопкой
**«Напрямую»** и по одной кнопке **«Через <метка>»** на каждый включённый relay (в
пользовательском и админском мастерах одинаково; у AmneziaWG шага нет — он не на 443).
Шаг подтверждения перепроверяет relay, так что выключенный за это время relay
отклоняется до того, как что-либо записано.

### Несколько relay в подписках

Новая all-in-one получает копию каждого участника через **каждый** relay, который
включён и «в подписках», группами в порядке `id` relay: сначала все прямые участники,
затем участники через relay №1, затем через relay №2 и т. д. — внутри группы обычный
порядок участников (basic: 2 в группе, extended: 5). Участник через relay получает
кружок своего прямого близнеца. См. [docs/subscription.ru.md](subscription.ru.md).

## Настройки

Полный справочник: [Конфигурация → Relay](configuration.ru.md#relay).

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `RELAY_HEALTH_INTERVAL` | `300` | Период проб, секунды; `0` = выключено. |
| `SERVER_FLAG_EMOJI` | `🇫🇮` | Флаг в названии одиночных ключей и участников basic. |
| `RELAY_ENABLED`, `RELAY_NAME`, `RELAY_HOST`, `RELAY_SOURCE_IPS` | — | **Устаревшие.** Только однократно заполняют пустую таблицу `relays` (см. выше); дальше игнорируются. |

**Настройки порта relay нет**: порт в relay-ссылке — это публичный порт самого
протокола (`XRAY_PUBLIC_PORT`, `HYSTERIA2_PORT`), потому что relay форвардит 1:1.

## Монитор доступности

При `RELAY_HEALTH_INTERVAL > 0` бот запускает **один** фоновый цикл для всех relay по
образцу монитора WARP. Каждый проход читает relay из БД (relay, добавленный или
изменённый в панели, подхватывается без рестарта) и проверяет каждый **включённый**
relay: TCP-подключение к `<host relay>:XRAY_PUBLIC_PORT` и TLS-handshake с
`server_hostname=XRAY_SNI` **с проверкой сертификата**. Бот работает на основном
сервере, поэтому проба уходит на relay и возвращается через его DNAT (hairpin); REALITY
не узнаёт в ней клиента и отдаёт её decoy, сертификат которого действителен для
`XRAY_SNI`. Поэтому прошедшая проба означает «TCP/443 через relay доходит до основного
inbound целиком» (проверено вручную: HTTP 200, `verify=0`, TLS ≈ 0,29 с).

- Одна проба длится не дольше 10 с и никогда не бросает исключение.
- Защёлка по времени — **своя у каждого relay** (`relays.id`): relay объявляется
  **недоступным** после одного интервала непрерывных отказов (две проваленные пробы
  подряд) и **снова доступным** после одного интервала непрерывных успехов. Каждый
  админ из `ADMIN_IDS` получает ровно одно сообщение на переход, с меткой, именем и
  host relay. Новый relay стартует как доступный; у выключенного или удалённого relay
  защёлка сбрасывается; состояние одного relay не влияет на другой.
- Последняя проба каждого relay (из цикла или «Проверить сейчас») показывается на его
  карточке; хранится только в памяти бота.
- Мёртвый relay **не** помечает Xray как degraded и не блокирует выдачу ключей.
- Каждая проба оставляет в error-логе Xray одну строку вида
  `REALITY: processed invalid connection from <IP relay>`. Это ожидаемо — так проба
  уходит в decoy.

## Ограничения

- **Детектор аномалий слеп к IP трафика через relay — так задумано.** L4 без PROXY
  protocol означает, что у каждого подключения через relay адрес relay; у Hysteria2
  поверх UDP адреса клиента нет вообще. Поэтому source IPs **всех** relay — включая
  выключенные — не учитываются вовсе (ни IP, ни его сеть/ASN); список перечитывается
  из БД в начале каждого цикла детекции. Inbound общий, так что это лишает IP-сигнала
  **любой** ключ, которым пользуются через relay, — в том числе прямой ключ, ссылку
  которого пользователь перенаправил на relay. Счётчик подключений `/online`
  Hysteria2 не затронут.
- **UDP не проверяется.** Монитор проверяет только TCP/443; Hysteria2 через relay не
  мониторится.
- **Порты 1:1.** Relay должен форвардить на те же номера портов, что публикует
  основной сервер.
- **Inbound общий.** Отдельного inbound, тега или учётных данных у relay нет; relay
  виден только в ссылке, которую держит пользователь.
- **URL подписки остаётся на основном домене.** Sub-URL (`:2096` в живом деплое)
  запрашивается с домена основного сервера, а не через relay; на relay указывают
  только ссылки внутри. Что нужно, чтобы перенести его за relay:
  [Проброс порта подписки](#проброс-порта-подписки-2096-через-relay).
- **Существующие подписки получают relay-участников только через админское
  приведение.** Добавление или включение relay существующие подписки само по себе не
  трогает. Админ-панель → «🔗 All-in-One» → «Дополнить все подписки по текущим настройкам»
  добавляет во все активные подписки участников через каждый relay, включённый и «в
  подписках» (а «Перевести все подписки в базовый вид» заодно убирает XHTTP-участников) — см.
  [docs/subscription.ru.md](subscription.ru.md#приведение-существующих-подписок).
