# Relay (ключи «через relay»)

**Relay** — второй вход на этот сервер: небольшой VPS (здесь — в России), который
форвардит клиентский трафик на L4 на основной сервер. Ключ «через relay» — обычный
ключ, ссылка которого указывает на relay вместо основного хоста. По умолчанию
выключено (`RELAY_ENABLED=false`).

## Топология

```
клиент ──TCP+UDP/443──▶ relay (RU VPS)
                          nftables DNAT tcp+udp dport 443 → <основной сервер>:443
                                         │
                                         ▼
                 основной сервер :443 ── xray vless-in (REALITY)
                                         ├─ XHTTP fallback → vless-xhttp-reality
                                         └─ (UDP) hysteria2
```

- Relay меняет только адрес назначения (DNAT) и маскарадит источник, поэтому
  основной сервер видит каждое подключение через relay как пришедшее с **egress-IP
  relay**. PROXY protocol нет — реальный адрес клиента до сервера не доходит.
- Клиент через relay попадает в **те же inbound'ы**, что и прямой: VLESS (TCP) и все
  профили VLESS (HTTP) на vless-in :443, Hysteria2 на UDP/443. На основном сервере
  про relay не знает ничего.
- Сама relay-инфраструктура (правила nftables, sysctl, VPS) **вне этого
  репозитория**. Её трекинг в `deploy/relay/` — отдельной PR.

### DNS

Заведите DNS-имя на relay — например, `relay.anycastedge.net` — в Cloudflare **без
проксирования** (DNS only, серое облако): HTTP-прокси Cloudflare не пропускает ни
REALITY, ни QUIC. Это имя и есть `RELAY_HOST`. Переезд relay на новый IP — это смена
A-записи: в ссылках имя, поэтому перевыпускать ключи не нужно.

## Что такое relay-ключ

Relay — **атрибут ключа** (`vpn_keys.relay`, `NULL` у прямого ключа), а не новый тип
ключа или транспорт:

- он создаётся тем же путём, что и прямой ключ, и получает свои uuid / secret /
  метку с обычным префиксом (`xray_tcp_*`, `xray_http_<профиль>_*`, `hy2_*`), поэтому
  `hy2_auth`, reconcile Xray (`XRAY_MANAGED_LABEL_RE`), статистика трафика и схема
  email-меток не затронуты;
- его ссылка отличается от ссылки прямого ключа ровно в двух местах: **хост**
  (`RELAY_HOST` вместо `XRAY_PUBLIC_HOST` / `HYSTERIA2_HOST`) и **название**
  (`_relay` после метки). Порт, REALITY `sni`/`pbk`/`sid`/`spx`/`fp`, `flow`,
  `path`/`mode`/`extra` XHTTP и `sni` Hysteria2 — те же: relay форвардит 1:1, и TLS
  по-прежнему терминируется на основном сервере его сертификатом / ключами REALITY;
- хост выбирается в одном месте (`services.relay.relay_link_host`) для всех путей —
  экран конфига, QR, мастер создания, кэш `public_payload.link`, подписка. Ключ, чей
  relay не равен включённому `RELAY_NAME`, **отклоняется** (`RelayUnavailable`) и
  никогда не перенаправляется молча на основной хост: ссылка, которая тихо обходит
  выбранный пользователем relay, — ровно та ошибка, от которой это защищает.

Пользователь выбирает это в мастере создания: после шага протокола (и профиля XHTTP),
пока `RELAY_ENABLED=true`, бот спрашивает **«Подключение: напрямую / через relay»**
(в пользовательском и админском мастерах одинаково; у AmneziaWG шага нет — он не на 443).

All-in-one, созданные при включённом relay, после прямых участников содержат
relay-копию каждого (basic 2 → 4, extended 5 → 10) — см.
[docs/subscription.ru.md](subscription.ru.md#два-вида-all-in-one).

## Настройки

Полная справка: [Конфигурация → Relay](configuration.ru.md#relay).

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `RELAY_ENABLED` | `false` | Предлагать relay-ключи / relay-участников all-in-one. |
| `RELAY_NAME` | `ru1` | Значение в `vpn_keys.relay`. Не переименовывать, когда ключи уже есть. |
| `RELAY_HOST` | — | DNS-имя (рекомендуется) или IPv4 relay. Обязателен при включении. |
| `RELAY_SOURCE_IPS` | — | Список egress IPv4/CIDR relay. Обязателен при включении. |
| `RELAY_HEALTH_INTERVAL` | `300` | Период проб, секунды; `0` = выключено. |
| `SERVER_FLAG_EMOJI` | `🇫🇮` | Флаг в названии одиночных ключей и участников базовой подписки. |

**Отдельной настройки порта relay нет**: порт в relay-ссылке — публичный порт
протокола (`XRAY_PUBLIC_PORT`, `HYSTERIA2_PORT`), потому что relay форвардит 1:1.

## Монитор здоровья

При `RELAY_ENABLED=true` и `RELAY_HEALTH_INTERVAL > 0` бот запускает фоновую пробу по
образцу WARP-монитора: каждый интервал открывает TCP-соединение к
`RELAY_HOST:XRAY_PUBLIC_PORT` и проходит TLS-handshake с `server_hostname=XRAY_SNI`,
**проверяя сертификат**. Бот работает на основном сервере, поэтому проба уходит на
relay и возвращается через его DNAT (hairpin); REALITY не узнаёт в ней клиента и
отдаёт её decoy, сертификат которого валиден для `XRAY_SNI`. Значит, успешная проба —
это «TCP/443 через relay доходит до основного inbound насквозь» (проверено руками:
HTTP 200, `verify=0`, TLS ≈ 0,29 с).

- Одна проба длится не больше 10 с и никогда не бросает исключение.
- Latch по времени: relay объявляется **упавшим** после одного интервала непрерывных
  неудач (две неудачные пробы подряд) и **поднявшимся** — после одного интервала
  непрерывных успехов. Каждый админ из `ADMIN_IDS` получает ровно одно сообщение на
  каждый переход.
- Упавший relay **не** помечает Xray degraded и не блокирует выдачу ключей.
- Каждая проба оставляет в error-логе Xray строку вида
  `REALITY: processed invalid connection from <IP relay>`. Это ожидаемо — так
  выглядит проба, отданная decoy.

## Ограничения

- **Детект аномалий слеп по IP для трафика через relay — by design.** L4 без PROXY
  protocol значит, что каждое подключение через relay несёт адрес relay; у Hysteria2
  поверх UDP адреса клиента нет вообще. Поэтому `RELAY_SOURCE_IPS` не учитываются
  никогда (ни IP, ни его сеть/ASN). Inbound общий, так что это снимает IP-контроль с
  **любого** ключа, которым пользуются через relay, — включая прямой ключ, который
  пользователь вручную перенаправил на relay. Счётчик `/online` у Hysteria2 не затронут.
- **UDP не пробуется.** Монитор проверяет только TCP/443; Hysteria2 через relay не
  мониторится.
- **Порты 1:1.** Relay должен форвардить на те же номера портов, что публикует
  основной сервер.
- **Inbound общий.** Отдельного inbound'а, тега или учётки на relay нет; relay виден
  только в ссылке, которая на руках у пользователя.
- **Адрес подписки остаётся на основном домене.** Sub-URL (`:2096` на живом сервере)
  запрашивается с домена основного сервера, а не через relay; на relay указывают
  только ссылки внутри неё.
- **Существующие all-in-one получают relay-участников только через админское
  приведение.** Само включение `RELAY_ENABLED=true` существующие bundle не трогает.
  Админ-панель → «🔗 All-in-One» → «Дополнить все подписки по текущим настройкам»
  добавляет relay-участников во все активные bundle (а «Перевести все подписки в базовый
  вид» заодно убирает XHTTP-участников) — см.
  [docs/subscription.ru.md](subscription.ru.md#приведение-существующих-подписок).
- **Выключение relay** делает ссылки relay-ключей недоступными (бот показывает ошибку
  вместо ссылки) и убирает relay-участников из подписок (warning в логе); прямые
  ключи и прямые участники не затронуты. После обратного включения всё возвращается
  как было.
