# Установка на чистый сервер

`scripts/install.sh` одной командой превращает чистый VDS с Ubuntu 24.04 в работающего бота.
Он задаёт два вопроса — режим и токен бота, — а всё дальнейшее происходит в Telegram.

🇬🇧 English version: [install.md](install.md)

## Однострочник

Скачайте установщик и контрольную сумму из последнего релиза на GitHub, проверьте, запустите:

```bash
curl -fsSLO https://github.com/Egor051/vpnbot/releases/latest/download/install.sh && curl -fsSLO https://github.com/Egor051/vpnbot/releases/latest/download/SHA256SUMS && sha256sum -c --ignore-missing SHA256SUMS && sudo bash install.sh
```

Оба файла прикладываются к каждому релизу `v*` workflow `.github/workflows/release-installer.yml`.
Контрольная сумма ловит оборванную или перепутанную загрузку; от скомпрометированного аккаунта
GitHub она не защищает (этого не может ничто, что лежит там же). Никогда не запускайте скрипт с
ветки через `curl … | bash`: запускать нужно выпущенный файл, который вы проверили.

> Первый релиз с установщиком и claim — следующий после `v3.0.0`. Пока он не вышел, в `latest`
> нет `install.sh`. Возьмите `scripts/install.sh` на фиксированном коммите
> (`https://raw.githubusercontent.com/Egor051/vpnbot/<commit>/scripts/install.sh`) и запустите с
> `INSTALL_REF=<тот же коммит>`; ref, в коде которого нет поддержки claim, установщик отвергает.

## Что он спрашивает

1. **Режим** — `1) основной сервер` или `2) relay`. В режиме relay спрашивается только
   **pairing-код**, который бот показывает в «🧙 Мастер настройки → 🛰 Relay → ➕ Добавить relay»
   (ни токена, ни Telegram ID — relay не обращается к Telegram); однострочная команда бота
   запускает его как `install.sh --relay` с кодом в stdin. Подробно:
   [relay.ru.md](relay.ru.md#установка-relay-одной-командой).
2. **Токен бота** от [@BotFather](https://t.me/BotFather), ввод скрыт. Он должен иметь вид
   `123456789:AA…`, и Telegram должен его принять (`getMe`); три попытки. Токен никогда не
   попадает в argv процесса (curl читает его из конфига на stdin), в лог установки и на экран.

## Что он делает

Сначала только чтение — предусловия: root, Ubuntu 24.04, `x86_64` или `aarch64`, systemd как
init, ≥ 2 ГиБ свободно под `/opt`, доступны `github.com`, `pypi.org` и Bot API.

Затем для основного сервера:

| Шаг | Результат |
|---|---|
| apt | `git python3-venv ca-certificates curl` и `qrencode`, если доступен |
| checkout | `/opt/vpn-service` на **последнем release-теге** (переопределяется `INSTALL_REF`) |
| venv | `/opt/vpn-service/.venv` из `constraints-hashed.txt` с `--require-hashes` |
| `.env` | из `.env.example`: токен, `ADMIN_IDS=` (пусто), все `*_ENABLED=false`; `root:root 0600` |
| data, logs | `/opt/vpn-service/data`, `/opt/vpn-service/logs`, `0700` |
| хелпер | `/usr/local/sbin/vpn-bot-db-perms` (`ExecStartPre` юнита) |
| юнит | `deploy/vpn-bot.service` как есть → `/etc/systemd/system/vpn-bot.service`, enabled |
| claim | `/etc/vpn-bot/claim.json`, см. ниже |

Модель привилегий — та, что в `deploy/vpn-bot.service` (root, Xray API mode); установщик её не
меняет и не создаёт пользователя `vpn-bot` (root-модели он не нужен). Ни один протокол не
ставится и не включается: Xray, AmneziaWG, Hysteria2, SOCKS5 и MTProto выключены, и бот без них
стартует чисто.

**Готовность** проверяется по факту, а не по таймеру: установщик запоминает размер `bot.log` в
байтах до старта и ждёт — не дольше 90 с — строку aiogram `Run polling for bot @…` после этого
смещения. Упавший юнит или лишний рестарт сразу прерывают ожидание. Затем тот же диапазон
сканируется на `ERROR`, `CRITICAL` и `Traceback`; любое из них — провал установки.

В конце печатаются ссылка для claim и QR-код.

## Claim первого суперадмина

`ADMIN_IDS` остаётся пустым. Вместо этого установщик генерирует 128-битный код и печатает

```
https://t.me/<ваш_бот>?start=claim_<код>
```

и ту же ссылку QR-кодом. Откройте её в Telegram **с аккаунта, который должен стать
суперадмином**, и нажмите «Старт». Этот аккаунт — суперадмин; дальше — в админ-панели (`/admin`).

- `/etc/vpn-bot/claim.json` (root, `0600`) хранит только `sha256(код)` и срок действия —
  **30 минут**. Сам код показывается один раз в вашем терминале и нигде не хранится.
- Ссылка срабатывает один раз, только в личном чате и только пока у бота **вообще нет
  суперадмина** — ни в `ADMIN_IDS`, ни забравшего бота, ни пользователя с ролью SUPERADMIN. На
  сервере с заданным `ADMIN_IDS` claim полностью инертен, есть `claim.json` или нет.
- На неверную, просроченную или использованную ссылку — один общий ответ без причины. Попытки
  ограничены (5 в час на пользователя, 20 в час всего). Код не попадает ни в один лог.
- Фактические суперадмины — `ADMIN_IDS` ∪ забравшие бота пользователи (таблица
  `claimed_superadmins`). Новый суперадмин сразу получает все уведомления, без рестарта.

Ссылка истекла или потерялась? Выпустите новую — больше эта команда ничего не делает:

```bash
sudo bash install.sh --reclaim
```

Если нет ни `ADMIN_IDS`, ни забравшего бота суперадмина, ни ожидающего claim, бот при каждом
старте пишет громкий WARNING `NO SUPERADMIN`.

## Атомарность: откат по manifest

Каждый каталог, файл, заменённый файл и юнит, который создаёт установщик, дописывается в
manifest **до** того, как появляется. Любой сбой — упавшая команда, Ctrl‑C, `SIGTERM` —
откатывается строго по этому manifest в обратном порядке: юнит останавливается и
отключается, файлы и `/opt/vpn-service` удаляются, заменённые файлы возвращаются. apt-пакеты
никогда не удаляются (они могли стоять и раньше); откат только пишет их в лог.

Лог и manifest остаются для разбора:

```
/var/log/vpn-bot-install.<timestamp>.log        # токен и код claim вычищены
/var/log/vpn-bot-install.<timestamp>.manifest
```

Одновременно работает только один установщик (`flock` на `/run/vpn-bot-install.lock`), и он
не запускается, пока идёт деплой (`vpn-bot-deploy.service`).

## Повторный запуск: repair

На сервере, где уже есть `/opt/vpn-service` с `.env`, установщик работает в режиме **repair**:

- `.env` и база данных не записываются никогда (проверка суперадмина открывает БД только на
  чтение);
- хелпер db-perms и юнит переустанавливаются из checkout, бот перезапускается и проверяется
  так же, как после установки;
- новая ссылка для claim выпускается, только если суперадмина всё ещё нет.

Неудачный repair откатывает заменённые файлы и перезапускает бота с ними.

## Переменные окружения

| Переменная | Значение |
|---|---|
| `INSTALL_REF` | Тег или коммит вместо последнего релиза. |
| `INSTALL_REPO` | Git URL для клонирования (по умолчанию — этот репозиторий на GitHub). |
| `TELEGRAM_API_BASE` | Сервер Bot API (по умолчанию `https://api.telegram.org`). Не-дефолтное значение пишется и в `.env`, чтобы бот ходил туда же. |
| `INSTALL_SELFTEST=1` | Точка для тестов: определить все функции и вернуться (`tests/test_install_script.py`). |
| `INSTALL_INJECT_FAILURE=<шаг>` | Точка для проверки отката в CI. На настоящей установке не задавать. |

Коды выхода: `0` готово · `1` ошибка (и откат) · `2` usage (неизвестный аргумент).

`--relay` (код в stdin) и `--relay-update` (его запускает `update` агента relay) — точки входа
режима relay: [relay.ru.md](relay.ru.md#установка-relay-одной-командой).

## После установки

Бот работает, администрирование — из Telegram. Backend'ы и hardening хоста установщик
сознательно **не** ставит. Для полного production-хоста (backend'ы протоколов, UFW, host check,
SSH-порт) следуйте [deployment.ru.md](deployment.ru.md); дальнейшие обновления — через
`scripts/redeploy.sh`, который деплоит `origin/main`.

## Как это проверяется

- `tests/test_install_script.py` гоняет каждую функцию через `INSTALL_SELFTEST` на заглушках
  системных команд: работа с токеном, `.env`, файл claim ровно в том формате, который читает
  бот, manifest и откат, готовность, проверка суперадмина только на чтение.
- CI-job `installer-e2e` запускает весь установщик от root на настоящей VM ubuntu-24.04 с
  systemd против mock Bot API (`tests/e2e/`): режим relay с плохим кодом ничего не меняет; сбой, внесённый
  после старта бота, не оставляет ни одного пути из manifest; настоящая установка активна с
  `NRestarts=0`; `/start claim_<код>` делает оператора суперадмином, а повторный claim
  отклоняется; повторный запуск — repair, после которого `.env` и `vpn.db` байт-в-байт те же.
