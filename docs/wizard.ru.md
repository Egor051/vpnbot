# Мастер настройки и второй фактор TOTP

В админ-панели два новых раздела, оба **только для SUPERADMIN**:

* **🧙 Мастер настройки** — фиксированные root-helper'ы, каждый запуск идёт в своём
  systemd-юните: сначала план, затем apply → verify → rollback при сбое.
* **🔐 Безопасность** — второй фактор (TOTP) суперадмина, который спрашивается перед
  опасными действиями.

🇬🇧 English version: [wizard.md](wizard.md)

## Что бот может и чего не может

Бот никогда не выполняет переданную ему команду, кнопки «shell» нет. Режим — это
фиксированный набор helper'ов из [`scripts/wizard/`](../scripts/wizard/), которые
`deploy.sh` ставит в `/usr/local/sbin` (`OUT_OF_REPO_HELPERS`, политика `required`), а на
свежем сервере — `scripts/install.sh` (`INSTALL_HELPERS`, те же файлы, откатываются
вместе с остальным при неудачной установке):

| Установленный helper | Роль |
|---|---|
| `vpn-bot-wizard` | Единственная точка входа для бота: `launch --mode M --run N --phase plan\|execute [--param k=v]...` |
| `vpn-bot-wizard-lib` | Общая библиотека (таблица режимов, status-файл, лог, редакция, dead-man, бэкапы) |
| `vpn-bot-wizard-selfcheck` | Режим «Самопроверка» |
| `vpn-bot-wizard-dump` | Режим «Диагностический дамп» |
| `vpn-bot-wizard-update` | Режим «Обновить бота» |
| `vpn-bot-totp-reset` | Аварийный сброс TOTP (root CLI, бот его не вызывает) |

В модели helper-nonroot бот обращается к лаунчеру через одну строку sudoers
(`deploy/sudoers.d/vpn-bot.example`):

```
/usr/local/sbin/vpn-bot-wizard launch *
```

Запущенный через sudo, лаунчер наследует mount namespace бота — `ProtectSystem=strict` в
`deploy/vpn-bot.nonroot.example.service` делает там `/run`, `/var/lib` и `/var/log`
доступными только на чтение, — поэтому `launch` сначала перезапускает себя в mount
namespace PID 1 (`nsenter --mount=/proc/1/ns/mnt`), так же как `vpn-bot-ufw-apply`.

Лаунчер заново проверяет всё по своей таблице (`MODES` в `vpn-bot-wizard-lib`):
неизвестный режим, номер запуска не положительное целое, неизвестный параметр,
значение вне типа (диапазон целого, `0`/`1`, перечисление) — отказ с кодом 2 **до**
любого действия. Бот проверяет те же параметры раньше (`services/wizard_modes.py`);
тест держит обе таблицы одинаковыми.

## Запуск

1. Бот вставляет строку в `wizard_runs` с `active = 1`. UNIQUE-индекс по `active` —
   это **глобальный lock**: пока один запуск активен, второй не начнётся (два быстрых
   нажатия не выиграют оба).
2. Бот просит лаунчер начать фазу. Лаунчер отказывает, пока активен любой юнит
   `vpn-bot-wizard-*` или занят `/run/vpn-bot-wizard.lock`, пишет первую строку
   статуса и запускает фазу **только** через
   `systemd-run --unit=vpn-bot-wizard-<id> --collect`. Поэтому запуск переживает
   рестарт бота — а режим `update` его сам и вызывает.
3. Внутри юнита `vpn-bot-wizard run` держит `/run/vpn-bot-wizard.lock` и ведёт
   helper режима по контракту:

   | Фаза | Шаги | Итог |
   |---|---|---|
   | `plan` | `<helper> plan` — dry-run, печатает, что изменится | `planned` (ждёт «✅ Применить» / «✖️ Отменить», 30 мин) или `failed` |
   | `execute` | `<helper> apply`, затем `<helper> verify`; при любом сбое `<helper> rollback` | `succeeded`, `rolled_back` или `failed` |

   Режим только для чтения не ждёт подтверждения и сразу идёт в `execute`; его
   `rollback` удаляет только собственный артефакт, запуск остаётся `failed`.
4. Прогресс — JSON-строки в `/var/lib/vpn-bot-wizard/<id>.status` (root, 0644). Бот
   читает его каждые 3 с, редактирует **одно** сообщение с прогрессом и превращает его
   в план или в итоговый отчёт. Последняя строка — всегда `{"event": "finished"}`;
   юнит, завершившийся без неё (убит), делает запуск `failed`.
5. Вывод каждого шага, после редакции, идёт в `/var/log/vpn-bot-wizard/<id>.log`
   (root:vpn-bot 0640). «📄 Лог» присылает его файлом (с повторной редакцией).

Состояния `wizard_runs.state`: `planned`, `running`, `verifying`, `succeeded`,
`rolled_back`, `failed` и `cancelled` (план отклонён или истёк).

### После рестарта

При старте бот находит активный запуск, пишет в лог `Setup wizard: resuming run #N` и
доводит его до конца по status-файлу и юниту. Итоговый отчёт отправляется ровно один
раз (`wizard_runs.reported_at`) — в том числе когда бот упал между концом запуска и
отчётом. Монитор никогда не пишет traceback в `bot.log`: он работает ровно в том
окне, где `deploy.sh` после вызванного им рестарта сканирует лог.

### История

«📜 История» — список запусков со статусами; у каждого своя карточка, лог и — для
дампа — файл. Каждое действие — в audit log (сущность `wizard`):
`wizard_run_started`, `wizard_plan_ready`, `wizard_run_confirmed`,
`wizard_run_finished`, `wizard_log_sent`, `wizard_schedule_changed`.

## Режимы

### 🩺 Самопроверка (только чтение)

Ничего не меняет. Каждая проверка — зелёный / жёлтый / красный пункт:

| Проверка | Красный | Жёлтый |
|---|---|---|
| `listeners` — `vpn-bot-ufw-apply listeners` | публичный TCP-listener, который набор правил firewall не разрешает и не объявляет закрытым | нет вердикта / helper не установлен |
| `warp` — только если WARP развёрнут (`/etc/amnezia/out-warp.conf` или включён `warp-routes`) | у `out-warp` нет fwmark-таблицы, нет `ip rule` с ней или в ней нет default route | — |
| `failed_units` — `systemctl --failed` | любой упавший юнит | — |
| `certs` — все сертификаты acme.sh, `/etc/hysteria/cert.pem`, `SUBSCRIPTION_TLS_CERT` | < 7 дней | < 21 дня (acme.sh продлевает за 30); у acme.sh нет `Le_ReloadCmd` |
| `helpers` — `OUT_OF_REPO_HELPERS` этой роли против checkout | нет `required`-helper'а | установленная копия отличается (следующий деплой исправит) |
| `perms` — `DB_PATH` (0600) и его каталог (0700), владелец `vpn-bot`, если такой есть; `.env` — владелец root, не доступен всем, не group-writable | любое отклонение | — |
| `disk` — `/`, `/var`, checkout | < 1 ГиБ или < 5 % свободно | < 15 % свободно |
| `reboot` — `/var/run/reboot-required` | — | нужна перезагрузка (со списком пакетов) |

**Ежедневный запуск.** «⏰ Ежедневная самопроверка» (хранится в `schema_meta`,
`wizard_selfcheck_daily`) раз в 24 часа запускает самопроверку, когда ничего другого не
идёт. Сообщение всем суперадминам — **только если** есть жёлтый или красный пункт или
сам запуск не удался; полностью зелёный день проходит молча.

### 📦 Диагностический дамп (только чтение)

Собирает в `/var/lib/vpn-bot-wizard/<id>.dump.txt` (root:vpn-bot 0640): версии (ОС,
ядро, python3, xray, hysteria, systemd), checkout (`HEAD`, последний коммит, чистый ли),
живой `schema_version` против `CURRENT_SCHEMA_VERSION` checkout'а, юниты,
`systemctl --failed`, listeners (`ss`), `ip rule` / `ip -6 rule`, хвост `bot.log` и
`error.log` Xray (параметр `lines`, 20–1000, по умолчанию 200).

Хвост лога оценивается по **времени последней строки с ERROR** («last ERROR at …
(3 h ago)»), а не по их количеству. Метки времени `bot.log` несут смещение UTC (локальное
время, `%z`) и читаются с ним; у Xray смещения нет — это локальное время хоста; обе
показываются в UTC.

Всё проходит через шаблоны редакции `utils/redact.py` (токены бота, ключи, пароли,
`secret=`, учётные данные в URL, длинный hex). `verify` перепроверяет файл и
отказывает, если шаблон всё ещё находится; бот редактирует ещё раз перед отправкой.
Дамп спрашивает код TOTP (он выносит топологию хоста за его пределы).

### ⬆️ Обновить бота

Тонкая обёртка над единственным поддерживаемым путём редеплоя, `scripts/redeploy.sh`:

* **plan** — `git fetch origin main`; коммиты `HEAD..origin/main`,
  `CURRENT_SCHEMA_VERSION` обеих версий и живая схема; затем `CHECK=1 redeploy.sh`
  (deploy.sh `PHASE1_ONLY=1`: вся Phase 1 только на чтение, включая тесты). `HEAD` уже
  **равен** `origin/main` (полные SHA — та же проверка, что в deploy.sh) — делать нечего,
  запуск на этом заканчивается. Checkout *впереди* `origin/main` (локальный коммит) — не
  no-op: план предупреждает, что деплой сбросит checkout и эти коммиты пропадут.
  План запоминает точную ревизию `origin/main`, которую описывает.
* **подтверждение** (TOTP) → **apply** — только эта ревизия: снова `git fetch origin
  main`, и если `origin/main` сдвинулся после плана (другие коммиты, возможно, другая
  миграция, чем подтверждённая), ничего не деплоится, запуск завершается ошибкой
  «запустите обновление заново». Затем `redeploy.sh`. `deploy.sh` останавливает и
  перезапускает бота; запуск продолжается в своём юните. Пуш в те секунды, что между
  этой проверкой и собственным fetch в redeploy.sh, verify показывает («deployed X, the
  plan was for Y»), а не скрывает.
* **verify** — `===== DEPLOY OK =====` в выводе и активный `vpn-bot.service`.
* **rollback** — `deploy.sh` откатывается сам (код, venv, БД, конфиги, юнит) и печатает
  `===== ROLLBACK REPORT =====`; шаг передаёт его и проверяет, что бот работает
  (`rolled_back`). Нет отчёта — deploy.sh остановился до Phase 2 (ничего не изменено)
  или не завершился — это `failed`: смотрите лог.

Мастер вызывает `redeploy.sh` с `REDEPLOY_ATTACH=pipe`: `systemd-run --wait --pipe`
вместо `--pty` (терминала нет) под `set -o pipefail`, так что обёртка ждёт и выходит с
кодом deploy.sh. Вердикт всё равно читается из текста отчёта — как его читает оператор.
Параметр `force` (`0`/`1`) — это `FORCE=1`.

### 🛰 Relay

Это не режим root-helper'ов: relay, которые бот ставит и ведёт сам по SSH, — pairing-код, одна
команда для relay (`scripts/install.sh --relay`), затем статус, обновление, порты/цель и удаление
из карточки relay. Lock запусков мастера он не занимает. Подробно:
[relay.ru.md](relay.ru.md#установка-relay-одной-командой).

## Библиотека helper'ов

`vpn-bot-wizard-lib` — основа будущих режимов (смена IP или домена, восстановление):

* **dead-man** — `deadman_arm(run, seconds, helper, params)` взводит
  `systemd-run --unit=vpn-bot-wizard-<id>-deadman --on-active=<N> --collect <helper>
  rollback --run <id> --deadman`; `deadman_disarm` останавливает таймер. Шаг, который
  трогает сеть, сначала взводит его — потерянная SSH-сессия не станет концом истории.
  Режимы этого релиза сеть не трогают; `update` опирается на собственный откат deploy.sh.
* **бэкап перед изменением** — `backup_paths(run, paths)` пишет tar.gz с манифестом
  sha256 в `/var/lib/vpn-bot-wizard/backups/<id>/` (0600); `restore_backup(archive)`
  возвращает файлы с их правами и владельцами.
* **лог** — `/var/log/vpn-bot-wizard/<id>.log`, каждая строка после редакции.

Test seam: `VPN_BOT_WIZARD_SELFTEST=1` переносит все пути под `VPN_BOT_WIZARD_ROOT` и
отказывает любой команде, которая не является заглушкой в
`VPN_BOT_WIZARD_SELFTEST_BIN`. В production этих переменных нет (sudo сбрасывает
окружение, systemd запускает юнит с чистым).

## TOTP

### Включение

«🔐 Безопасность → 🔐 Включить TOTP» или необязательный шаг, который бот предлагает
сразу после успешного claim первого суперадмина ([install.ru.md](install.ru.md)):

1. Бот показывает секрет QR-кодом (`otpauth://totp/vpnbot:<user>?secret=…`, SHA1,
   6 цифр, 30 с) и текстом в base32 с той же ссылкой — для приложения без сканера.
2. Вы отправляете текущий 6-значный код.
3. TOTP включён, и **10 одноразовых резервных кодов** показываются **один раз**.
4. «✅ Я сохранил коды» удаляет сообщение с кодами. Сообщения с секретом и QR
   удаляются, как только код принят; каждое сообщение с введённым кодом удаляется,
   как только бот его прочитал.

### Хранение

* Секрет хранится только зашифрованным Fernet (`totp_credentials.secret_enc`). Ключ —
  `/etc/vpn-bot/totp.key`, создаётся при первом включении, права 0600, владелец —
  пользователь бота; бот отказывается от файла-ключа, если это симлинк, не обычный файл
  или он доступен кому-то ещё. В модели helper-nonroot бот не может писать в
  `/etc/vpn-bot`; создайте ключ один раз от root (ключ Fernet — 32 случайных байта в
  url-safe base64):

  ```bash
  python3 -c 'import base64, os; print(base64.urlsafe_b64encode(os.urandom(32)).decode())' | sudo install -o vpn-bot -g vpn-bot -m 0600 /dev/stdin /etc/vpn-bot/totp.key
  ```

* Файл ключа, пропавший при живых секретах, никогда не заменяется новым (это скрыло бы
  потерю): проверка отказывает и указывает на сброс ниже.
* Резервные коды хранятся только как `hashlib.scrypt` (N=2¹⁴, r=8, p=1, своя 16-байтная
  соль на код); у погашенного кода есть `used_at`, и он больше не подходит.
  «🔐 Безопасность» показывает остаток. «🔑 Перевыпустить резервные коды» требует
  **TOTP**-код (резервного мало) и аннулирует старые.
* `/etc/vpn-bot` входит в системный offsite-бандл, так что ключ уезжает вместе с
  зашифрованными бэкапами.

### Проверка кода

* Окно ±1 шаг (±30 с).
* Replay: запоминается time-step последнего принятого кода (`last_used_step`); код этого
  шага или более раннего отклоняется — и после рестарта тоже.
* 5 неверных подряд → ввод заблокирован на 15 минут и алерт всем суперадминам. Счётчик и
  блокировка — в БД: рестарт их не снимает. Верный код обнуляет серию.

### Где спрашивается

Только если у суперадмина TOTP включён (фактор — по желанию):

| Действие | Где |
|---|---|
| удаление протокола с сервера | «Модули протоколов → Удалить с сервера» (последняя кнопка) |
| отключение протокола (удаляет все его ключи и доступы) | «Модули протоколов → Отключить» (последняя кнопка) |
| удаление relay вместе с его ключами | «Relay → Удалить → вместе с ключами» |
| мастер: диагностический дамп | запуск и файл дампа из истории |
| мастер: обновление бота | запуск и «✅ Применить» |
| мастер → Relay: выпуск pairing-кода | «➕ Добавить relay» |
| мастер → Relay: обновление relay | «⬆️ Обновить» |
| мастер → Relay: смена портов / цели relay | «⚙️ Порты / цель» (шаг ввода текста проверяет elevation ещё раз) |
| мастер → Relay: удаление relay (uninstall на relay) | последняя кнопка |

Верный код даёт **elevation** на 5 минут: в этом окне код больше не спрашивается.
Elevation живёт только в процессе бота — рестарт его сбрасывает. Запрос кода
превращается в «▶️ Продолжить», которая снова нажимает исходную кнопку. Будущие опасные
действия (ротации, смена IP/домена, восстановление) регистрируются в
`DANGEROUS_ACTIONS` (`bot/totp_gate.py`). Audit (сущность `security`):
`totp_enrollment_started`, `totp_enabled`, `totp_verified`, `totp_backup_code_used`,
`totp_verify_failed`, `totp_locked`, `totp_backup_codes_reissued`, `totp_disabled`,
`totp_reset_cli`.

### Отключение

«🚫 Отключить TOTP» требует TOTP-код или резервный код.

### Аварийный сброс

Потеряны и телефон, и резервные коды: на сервере, от root,

```bash
sudo vpn-bot-totp-reset <telegram_id>
```

Спрашивает подтверждение в терминале (`--yes` пропускает вопрос; без терминала `--yes`
обязателен), одной транзакцией удаляет TOTP пользователя и все резервные коды и пишет
audit-строку `totp_reset_cli`. База — `DB_PATH` из `/opt/vpn-service/.env` (`--db PATH`
переопределяет). Бот читает состояние TOTP из БД при каждой проверке, так что сброс
действует сразу; elevation, который бот ещё держит, истекает за 5 минут (или
`sudo systemctl restart vpn-bot`). Включить TOTP заново — в «🔐 Безопасность».
